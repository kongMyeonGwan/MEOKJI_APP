## 서버를 스프링부트로 옮기는 중 (2026-09-27)

학원이 서버를 스프링부트로 쓰기로 바뀌었다. `backend/`(FastAPI)를 **그대로 두고**
`backend-spring/` 을 따로 만들어 옮긴다. 브랜치는 `feature/spring-boot` 다.

```
backend/          FastAPI   :8000   포팅이 끝날 때까지 살려둔다
backend-spring/   Spring    :8080   여기
frontend/         React     :5173   손대지 않는다
db/                               스키마 그대로. 바꿀 것이 없다
```

### 왜 저장소를 새로 파지 않았나

옮겨야 할 것은 백엔드뿐인데, 새 저장소를 파면 안 옮겨도 되는 것까지 따라간다 —
프론트 77개 파일, `db/*.sql`, 그리고 이 문서다. 특히 이 문서를 두고 오면 조사
처리 · 최소단위 올림 · `use_yn` 소프트 삭제 · 오라클 함정을 옮기는 3주 동안
아무도 들춰보지 않게 된다.

그리고 포팅 작업의 실체는 **파이썬 코드를 옆에 놓고 한 줄씩 옮기는 것**이다.
원본이 같은 폴더에 있는 편이 압도적으로 편하다.

되돌릴 수 있는 쪽을 골랐다. 지금 저장소에서 시작했다가 따로 떼는 것은 폴더 하나
복사면 되지만, 새 저장소로 시작했다가 합치는 것은 히스토리를 붙이거나 버려야 한다.

### 고른 것

| 항목 | 선택 | 이유 |
|---|---|---|
| Spring Boot | 4.0.8 | MyBatis 스타터가 `[4.0.0, 4.1.0.M1)` 까지만 호환된다 |
| Java | 17 | 설치된 JDK 17.0.11 |
| 빌드 | Gradle **Wrapper** 9.7.1 | PC 에 Gradle 을 깔지 않는다. 팀원도 `gradlew` 만으로 빌드 |
| DB 접근 | **MyBatis** | 아래 참고 |
| 드라이버 | `ojdbc17` + HikariCP | JDK 17 호환 |
| 인증 | Spring Security + jjwt | 지금과 같은 방식 (Refresh Token 없음) |

**MyBatis 를 고른 이유가 이 스키마에 있다.** 모든 조회에 `use_yn='Y'` 가 붙고,
UNIQUE 가 제약조건이 아니라 함수 기반 인덱스이고, 중복 INSERT 는 `MERGE` 로
처리하고, 검색은 `LOWER(col) LIKE LOWER(:kw)` 다. JPA 로 우회하는 것보다 SQL 을
직접 쓰는 쪽이 맞다.

### 이름 규칙이 세 층이다

```
DB      snake_case   FOOD_NAME     스키마는 그대로 쓴다
자바    카멜          foodName      mybatis: map-underscore-to-camel-case
JSON    snake_case   food_name     jackson: property-naming-strategy
```

**가운데만 카멜이다.** 프론트 77개 파일이 `food_name` · `has_file` 을 그대로
읽고 있어서, 나가는 JSON 을 카멜로 바꾸면 **화면이 빈 값으로 뜨면서 에러도 안
난다.** React 가 없는 필드를 읽어 `undefined` 를 받고 그대로 그리기 때문이다.

### 0단계 — 정답지를 먼저 떴다

옮기기 전에 파이썬 서버의 응답 38개를 `backend-spring/src/test/resources/fixtures/`
에 떠뒀다. 이게 없으면 포팅이 "돌아가는 것 같다" 로 끝난다.

정상 응답만 담지 않았다. 401 · 404 · 409 · 422 · 501 의 본문도 같이 떴다 —
프론트가 `detail` 을 읽어 화면에 뿌리므로 오류 모양도 계약이다.

떠보니 프론트가 실제로 읽는 것은 `detail` 이 문자열이면 메시지, 배열이면 각
항목의 `loc` · `msg` 뿐이었다. Pydantic 이 같이 보내던 `type` · `input` · `ctx` 는
안 쓴다. 그래서 그 둘만 만들었다 — 안 쓰는 칸을 흉내내면 맞는지 확인할 수 없는
코드만 늘어난다.

### 기존 회원이 그대로 로그인된다

bcrypt 는 passlib 와 같은 알고리즘이라 저장된 해시(`$2b$...`)가 그대로 통한다.
비밀번호를 다시 만들 필요가 없다. 테스트가 이걸 확인한다 — `minji@example.com` 의
비밀번호는 파이썬이 만들어 저장한 것이고, 그 계정으로 로그인해 받은 `user` 객체가
정답지와 글자까지 같다.

토큰도 서로 통한다. 같은 HS256 · 같은 비밀키 · `sub` 에 회원 id 를 문자열로 담는
것까지 같아서, 한쪽에서 로그인해 받은 토큰으로 다른 쪽을 부를 수 있다. 응답을
비교할 때 이게 편하다.

### 로그인 필요 여부는 컨트롤러가 정한다

파이썬의 세 의존성을 애노테이션 하나로 옮겼다.

```
Depends(get_current_user)   ->  @LoginUser User me                      없으면 401
Depends(get_optional_user)  ->  @LoginUser(required = false) User me    없으면 null
Depends(get_admin_user)     ->  @LoginUser(admin = true) User me        아니면 403
```

`SecurityConfig` 에 주소 목록을 적지 않는다. 라우터를 추가할 때 두 곳을 고쳐야
하고, 한쪽만 고치면 조용히 열린다. `AuthController.me()` 에 null 검사를 한 번 더
둔 것도 같은 이유다 — `WebConfig` 에 리졸버 등록을 빼먹으면 `@LoginUser` 가 조용히
null 로 들어와서 로그인 검사가 사라진 채로 정상 동작하는 것처럼 보인다.

### post 를 review 로 — 표 이름에 맞췄다 (2026-09-29)

2026-09-04 스키마 v2 기록에 이렇게 적어뒀던 것을 닫는다.

> API 경로는 아직 `/api/posts` 다. 테이블만 `recipe_reviews` 로 바뀐 상태라
> 이름이 어긋나 있다. **프론트까지 함께 고칠 때 정리한다**

표는 `recipe_reviews` · `review_likes` · `review_comments` 인데 API 와 화면만
"post" 였다. 엔티티(`RecipeReview` · `ReviewComment` · `ReviewLike`)는 처음부터
맞아 있어서, 한 도메인에 두 이름이 섞여 있었다 - 어느 쪽이 무엇인지 매번
확인해야 한다.

    자바    PostController · PostService · dto/post/ · PostCreateRequest ...
            -> ReviewController · ReviewService · dto/review/ · ReviewCreateRequest
    주소    /api/posts/{postId}        -> /api/reviews/{reviewId}
    프론트  api/posts.js · PostWritePage · PostDetailPage · PostCard · PostAttachment
            -> api/reviews.js · ReviewWritePage · ReviewDetailPage · ReviewCard ...
    CSS     .post · .post__* · .post-card* -> .review · .review__* · .review-card*

공지(notices)는 표 이름이 그대로라 손대지 않았다.

#### "post" 를 통째로 바꾸면 안 되는 자리가 있다

HTTP 메서드도 post 다. `@PostMapping` · `client.post(` · `HttpMethod.POST` ·
MockMvc 의 `post(...)` 를 같이 바꾸면 컴파일이 깨지거나 - 더 나쁘게는 -
요청 메서드가 조용히 달라진다. 그래서 낱말 단위 식별자만 골라 바꿨고,
`client.post(` 가 들어 있는 파일에서는 단독 `post` 치환을 아예 막아뒀다.

#### 파이썬과 주소가 갈라졌다

`StubFixtureTest` 는 "파이썬과 같은 주소 20개" 를 지키는 테스트였다. 이제 후기
쪽은 다르다. 주석을 사실대로 고쳤다 - 파이썬은 곧 걷어내고, 그때 기준이 될
것은 이쪽이다. 정답지 `posts_not_implemented.json` 도
`reviews_not_implemented.json` 으로 옮기고 바뀐 이유를 파일 안에 적었다.

#### 지금이 가장 싼 시점이었다

게시판 담당자가 아직 `ReviewMapper` 를 만들지 않았다. 구현이 들어간 뒤였다면
주소 계약을 중간에 바꾸는 일이 됐을 것이다.

확인: 테스트 94건 · `vite build` 209 모듈 · 서버를 띄워 주소 확인.

### 자바를 계층별 폴더로 · 주입을 @Autowired 로 (2026-09-29)

팀원마다 맡은 자리가 있는데 파일 목록만 봐서는 어디에 무엇을 만들어야 할지
알 수 없었다. 화면(`pages/`)을 역할별로 나눈 것과 같은 이유다.

    controller/ 12 · service/ 14 · mapper/ 6 · dto/ 42(기능별로 한 겹 더)
    vo/ 9 · util/ 15 · common/ 4 · config/ 3 · security/ 3

`MeokjiApiApplication` 만 루트에 남겼다. 거기 있어야 컴포넌트 스캔이 돈다.

#### 폴더보다 흐름을 먼저 맞췄다

계층별로 나누기 전에 **계층 자체가 어긋나 있었다.** 컨트롤러 12개 중 둘
(`GameController` · `LikeController`)이 매퍼를 직접 불렀다. 하는 일이 단순해서
서비스를 두지 않았던 것인데, 폴더를 `controller/` · `service/` · `mapper/` 로
나누면 그 둘만 가운데를 건너뛰게 된다.

`GameService` · `LikeService` 를 만들어 끼웠다. 얇은 클래스가 되지만 **규칙이
예외 없이 하나인 게 낫다** — 어떤 컨트롤러는 거치고 어떤 것은 건너뛰면 새로
들어온 사람이 규칙을 코드마다 다르게 배운다. 트랜잭션 경계도 서비스로 내렸다.

`HealthController`(DB 가 살아있는지만 본다)와 `CatalogController`(JSON 을 읽어
그대로 내보낸다)는 그대로 뒀다. 서비스를 넣으면 껍데기만 늘어난다.

#### 생성자 주입 -> @Autowired 필드 주입

29개 중 28개를 바꿨다. `ApiException` 만 남는다 - 빈이 아니라 예외 값 객체다.

손으로 손본 것이 둘 있었다. `JwtProvider` 는 생성자에서 `AppProperties` 로
서명키를 만들고 있었는데, **필드 주입이면 생성자 시점에 아직 null 이라**
`@PostConstruct` 로 옮겼다. 키가 비면 서버가 아예 안 뜨는 동작은 그대로다.
`PasswordResetService` 는 `TransactionTemplate` 을 직접 `new` 하던 것을
스프링부트가 만들어 둔 빈 주입으로 바꿨다.

필드 주입은 `final` 을 못 붙이고 컨트롤러를 직접 생성해 테스트할 수 없다.
우리 테스트는 전부 `@SpringBootTest` + MockMvc 라 실제로 걸리는 곳은 없다.

#### 자동 분류로는 둘이 틀렸다

이름만 보고 나누면 `ApiExceptionHandler` 가 컨트롤러로 잡힌다 -
`@RestControllerAdvice` 가 `@RestController` 를 글자로 포함해서다. 실제로는 공통
오류 처리라 `common/` 이 맞다. `MeokjiApiApplication` 도 마찬가지로 걸렸다.
둘 다 손으로 빼뒀다.

#### 컴파일이 안 잡아주는 곳 둘

**매퍼 XML.** `namespace` 와 `resultType` 이 문자열로 클래스를 찾는다. 자바만
옮기고 XML 을 안 고치면 **컴파일은 지나가고 서버가 뜨다가 죽는다.** 6개 파일의
11개 참조를 같이 고쳤다.

**인라인 전체 경로.** `PriceService` 한 곳에 `import` 없이
`com.meokji.api.common.Numbers.round(...)` 라고 적혀 있었다. import 만 다시 쓰는
스크립트가 못 잡아서 컴파일 오류로 드러났다 - 이건 컴파일이 잡아줘서 다행이었다.

확인은 셋으로 했다. 컴파일 · 테스트 94건 · 그리고 **서버를 띄워 매퍼를 타는
주소 9개를 실제로 호출**했다. XML 이 틀리면 테스트가 아니라 여기서 드러난다.

### 파이썬을 걷어낼 준비 (2026-09-29)

지우기 전에 챙겨야 할 것 셋을 끝냈다. **아직 지우지는 않았다.**

#### 게시판 참고 구현은 git 에 있었다

처음에 "파이썬 `posts.py` 353줄이 담당자의 참고 구현" 이라고 봤는데 **틀렸다.**
열어보니 그쪽도 501 스텁이다 — 줄 수만 세고 내용을 안 봤다.

진짜 구현은 커밋에 남아 있다. 화면을 가데이터로 바꾸면서 걷어낸 것이다.

    e22853f  2026-09-18  소스 단계 낮추기   <- post_service.py 620줄, 구현이 살아 있다
    5576ddc  2026-09-18  가데이터           <- 여기서 37줄 스텁으로 바뀜

**이게 저장소를 새로 파면 안 되는 가장 큰 이유다.** 작업 트리에는 없고 히스토리에만
있어서, 새 repo 로 옮기는 순간 사라진다.

그 구현에서 동작 규칙을 뽑아 `docs/BOARD_SPEC.md` 에 적었다. DTO 만 봐서는 알 수
없는 것들이다 — 남의 글도 403 이 아니라 404 인 이유(그 번호가 존재한다는 사실이
새어나간다), 좋아요를 껐다 켤 때 새로 INSERT 하지 않고 껐던 행을 되살리는 이유
(함수 기반 UNIQUE), 인기 레시피가 한국 날짜로 잘리는 이유(9시간).

#### 데이터 파일은 테스트가 지키게 했다

`resources/data/*.json` 다섯 개는 파이썬에서 내보낸 표이고, `backend/` 를 지우면
이 파일이 원본이 된다. 내보내는 스크립트를 옮길까 했는데, 옮겨봐야 원본이 사라진
뒤에는 쓸 데가 없다. **필요한 건 "손으로 고쳐도 틀린 걸 알아채는 것"** 이다.

`DataFileTest` 9건을 만들었다. 개수 · 빠진 칸 · 좌표가 한국 안인지와,
**카탈로그와 레시피의 메뉴가 정확히 같은지**까지 본다.

마지막 검사가 핵심이다. 바로 앞에서 찾은 `크림 파스타` 버그가 정확히 그 종류였다 —
한쪽에만 있는 메뉴는 "추천은 되는데 눌러보면 404" 가 된다. 레시피 키 하나를 일부러
바꿔서 테스트가 실제로 잡는지 확인했다.

각 파일의 `_note` 도 고쳤다. 전에는 "파이썬 쪽을 고친 뒤 다시 내보낸다" 뿐이라
파이썬이 사라지면 말이 안 되는 안내였다. 지금은 두 상태를 다 적는다.

#### 문서의 파이썬 참조는 둘로 나눴다

54개 파일이 파이썬을 가리키는데, 전부 고치려다 그만뒀다. **대부분은 "어디서
왔는가" 를 적은 기록**이라 파이썬이 없어져도 말이 된다. 오히려 지우면 왜 이렇게
만들었는지가 사라진다.

실제로 깨지는 것은 **따라 하라고 적어둔 명령**뿐이다. 다섯 군데를 고쳤다.

정답지 38개를 다시 뜰 수 없다는 건 그냥 인정하고 적었다. **고정된 과거

### 데모 데이터 시드를 스프링으로 옮겼다 (2026-09-29)

파이썬을 걷어내기 전에 먼저 옮겨야 하는 것이었다. **스프링 테스트 85건이
`minji@example.com` 계정과 데모 기록을 전제로 도는데, 그걸 만드는 건 파이썬
`scripts/seed_demo.py` 뿐이었다.** 파이썬을 지우면 빈 DB 에서 테스트를 돌릴
방법이 사라진다.

`gradlew seedDemo` 로 돌린다. `@Tag("seed")` 가 붙어 있어 `gradlew test` 에서는
빠진다 — 평소 테스트마다 회원과 후기를 새로 만들 이유가 없다.

#### MockMvc 가 TestClient 자리다

파이썬이 DB 에 직접 INSERT 하지 않고 `TestClient` 로 API 를 부르는 이유를 그대로
가져왔다. 서버를 거쳐야 검증기 · FK · UNIQUE 가 실제로 돌고, 덤으로 "이 흐름이
지금도 도는가" 가 한 번 확인된다. `MockMvc` 가 같은 자리다 — 서버를 따로 띄우지
않으면서 컨트롤러 · 검증기 · 매퍼를 다 지난다.

가격 조회는 `@MockitoBean` 으로 막았다. 파이썬이 `price_api.kamis_offers` 를
갈아끼우는 자리다 — 시세는 DB 에 저장되지도 않는 값이라 데모 데이터와 상관없고,
인증키가 비면 `GET /api/recipes` 가 503 으로 끝난다.

관리자 승격만 SQL 을 직접 쓴다. 매퍼에 메서드를 만들지 않은 것은 **운영 코드에
"관리자로 승격" 이라는 길을 내지 않으려는 것**이다. 파이썬도 같은 이유로 거기만
raw SQL 이다.

#### MockMvc 는 퍼센트 인코딩을 풀어주지 않는다

`/api/recipes/크림 파스타` 를 부르려고 `URLEncoder` 로 감싸 붙였더니, 컨트롤러가
`%ED%81%AC%EB%A6%BC...` 를 <b>메뉴 이름 그대로</b> 받았다. 실제 서블릿 컨테이너는
풀어주지만 MockMvc 는 그러지 않는다. URI 변수로 넘겨야 한다.

    get("/api/recipes/{name}", food)      // 이렇게
    get("/api/recipes/" + encoded)        // 이러면 안 된다

#### 옮기다 파이썬 시드의 버그를 찾았다 — `크림 파스타`

시드가 확정하는 메뉴 셋 중 하나가 **`recipes.json` 에 없는 메뉴**였다. STEP 41 에서
레시피 100종을 다시 정의할 때 빠졌는데, 기존 DB 에는 그 전에 만들어진 행이 남아
있어 "이미 있음" 으로 건너뛰는 바람에 드러나지 않았다. 빈 DB 에 돌리면 3단계에서
404 로 죽는다.

기록을 하나 지우고 다시 돌려봐서 찾았다. **"이미 있으면 건너뛴다" 는 성질이
생성 경로를 가려준다** — 시드를 고칠 때는 지우고 한 번 돌려봐야 한다.

스프링 쪽은 `비빔국수` 로 바꿨다. 면 요리라 첨부용으로 그리는 그림(감아 올린 면)이
그대로 맞고, 색만 고추장 쪽으로 옮겼다. **파이썬 쪽은 고치지 않았다** — 곧 걷어낼
코드라 두 곳을 맞춰둘 이유가 없다. README 에 그 차이를 적어뒀다.

#### 소스 인코딩을 못박았다

`options.encoding = 'UTF-8'` 을 넣었다. 주석과 문자열에 한글이 많은데, 이걸 안
박아두면 기계의 기본 문자셋에 따라 javac 가 다르게 읽는다 — 영문 윈도우(cp1252)에서
받아 빌드하면 "이미 사용 중인 이메일입니다" 같은 문구가 깨진 채로 컴파일되고,
에러가 나지 않아서 응답을 눈으로 보기 전까지 모른다.

### 마지막 둘을 옮겼다 — 비밀번호 재설정 · 떨이 재료 (2026-09-28)

남겨뒀던 이유가 둘 다 "바깥이 필요해서" 였다. 하나는 메일 서버, 하나는 KAMIS 를
101번 부르는 일이다.

#### 비밀번호 재설정 — 시각 비교를 전부 SQL 로 모았다

만료(5분)와 재발송 제한(60초)은 "지금" 을 기준으로 판단한다. 그런데
`created_at` 은 DDL 의 `DEFAULT SYS_EXTRACT_UTC(SYSTIMESTAMP)` 가 찍는 **DB 시계**다.
그 "지금" 을 자바에서 만들면 두 시계를 견주게 되고, **조금만 어긋나도 재발송
제한이 59초가 되거나 61초가 되는데 에러가 나지 않아 알아채기 어렵다.**

그래서 비교를 매퍼로 내렸다. `findResendWaitSeconds` 가 남은 초를 돌려주고,
`findUsable` · `findVerified` 가 만료 조건을 SQL 안에 넣는다. 자바에는 시각을
만드는 코드가 한 줄도 없다.

파이썬은 만료 검사를 세 번 나눠서 한다(없음 · 이미 씀 · 만료). 셋 다 같은 400
문구로 끝나고, 발급 때마다 이전 코드를 지워서 행이 하나뿐이라 SQL 조건으로
합쳐도 결과가 같다.

#### `@Transactional` 이 조용히 아무 일도 안 할 뻔했다

메일은 **커밋 이후에** 보내야 한다. 발송에 성공했는데 DB 가 롤백되면 사용자는
코드를 받았는데 서버는 모르는 상태가 된다. 그래서 발급 부분만 따로 커밋하려고
`@Transactional(propagation = REQUIRES_NEW)` 를 붙인 메서드를 만들었는데,
**같은 클래스 안에서 부르면 프록시를 안 거쳐서 애노테이션이 무시된다.**

`TransactionTemplate` 으로 바꿨다. "이 블록만 묶고 그 뒤에 메일을 보낸다" 가
핵심인 자리라, 애노테이션보다 눈에 보이는 쪽이 낫다.

#### 옮기다 파이썬과 어긋난 곳을 하나 찾았다 — 비밀번호 바이트 검사

파이썬은 `check_password_bytes` 를 가입 · 비밀번호 변경 · 재설정 **세 곳**에서
부른다. 스프링은 가입에만 있었다. DTO 의 `@Size(max = 72)` 는 글자 수라서,
한글 비밀번호 25자면 75바이트가 되어 bcrypt 가 거부하고 **500 이 나간다.**

`auth/Passwords.java` 로 규칙을 한 곳에 모으고 세 곳에서 부르게 했다.

#### 떨이 재료 — 부르는 쪽을 기다리게 하지 않는다 (파이썬과 다르다)

파이썬은 기억해둔 것이 없으면 훑기가 끝날 때까지 기다렸다가 돌려준다. 비동기
서버라 그동안 다른 요청을 받을 수 있어서 가능한 방식이다.

스프링에서 그대로 하면 **톰캣 작업 스레드 하나가 1분 동안 통째로 묶인다.**
먼저 온 사람은 어차피 브라우저 쪽에서 먼저 끊긴다. 그래서 가진 것을 바로
돌려주고 훑기는 뒤에서 돌리게 했다 — 첫 요청은 빈 목록을 받고, 훑기가 끝난
뒤의 요청부터 값이 나온다. 화면은 빈 목록을 이미 견딘다.

대신 서버가 뜰 때 미리 한 번 훑는다. 다만 **기본값은 꺼짐**으로 뒀다 —
켜두면 `gradlew test` 를 돌릴 때마다 바깥 API 를 101번 두드린다.
`WARM_BARGAINS=true` 로 켠다.

#### 116개가 아니라 101개였다

파이썬 `unique_items()` 가 코드가 겹치는 이름을 하나로 줄인다. 표에는 같은
품목코드를 가리키는 이름이 여럿이라("대파"·"쪽파") 이름마다 물어보면 같은
응답을 두 번 받는다. 116 → 101 이고, 테스트가 이 숫자를 지킨다.

실제로 훑어보니 이렇게 나왔다.

    호박   -20.6%   796원/1개
    오이   -10.9%  1980원/10개
    쥬키니  -5.1%  1250원/1개
    (삼치 +9.4% · 버섯 +11.1% 은 파일에만 남는다)

오른 것도 파일에 남기는 것은 파이썬과 같다. 나중에 화면이 "오늘은 배추가
비싸요" 까지 말할 수 있게 열어둔 것이고, 자르는 것은 꺼내 쓰는 쪽이 한다.

#### 떨이 재료는 고른 메뉴에 영향을 주지 않는다

옮기면서 확인한 것이다. 원래 설계는 이 목록을 AI 프롬프트에 넣어 "이 재료를
쓰는 메뉴" 를 고르게 하는 것이었는데, **STEP 43 에서 AI 호출을 걷어내며 그 길이
끊겼다.** 지금 추천을 담당하는 `catalog_recommend_foods` 는 `context["bargains"]`
를 한 번도 읽지 않는다 — 유일하게 읽던 프롬프트 생성 부분이 주석 처리돼 있다.

그래서 스프링도 같게 뒀다. `use_bargains` 는 화면 위쪽 칩과 `condition` 문구를
만드는 역할만 한다. 재료를 실제로 점수에 반영하는 것은 이식이 아니라 새 기능이라
`FoodScorer` 에 규칙을 새로 만드는 일이 된다.

참고로 `BargainPick.jsx` 의 주석("AI 한테 넘기면 그 재료를 쓰는 메뉴를 골라준다")
은 STEP 43 이전 기준이라 지금은 사실과 다르다.

### 파이썬과 다른 곳을 하나 찾아 맞췄다 — `need_text`

조사가격이 없는 재료에서 파이썬은 `need_text` 가 `null` 이고 내 쪽은 `"0.5모"`
였다. 파이썬 `scale_offers` 가 `offers` 가 비면 빈 dict 를 돌려주고 `need_text` 는
기본값 `None` 으로 남는다 — 값을 알 수 있는데도 안 채우는 것이다.

프론트 동작은 같다. `PriceTable.jsx` 는 `min_unit` 이 참일 때만 `need_text` 를

프론트가 파이썬 기준으로 만들어져 있고, 정답지와 글자가 달라지면 비교할 때마다

### 옮기다 걸린 것들

| 무엇 | 어떻게 됐나 |
|---|---|
| Boot 4 는 **Jackson 3** | 패키지가 `com.fasterxml.jackson` 이 아니라 `tools.jackson` 이다 |
| `WRITE_DATES_AS_TIMESTAMPS` | Jackson 3 에서 `DateTimeFeature` 로 옮겼다. `spring.jackson.serialization` 아래에 적으면 **서버가 뜨지 않는다** |
| XML 주석의 `--` | 매퍼 XML 주석에 `-----` 를 그으면 `SAXParseException` 으로 매퍼를 아예 못 읽는다 |
| **405 가 500 으로 나갔다** | `ResponseStatusException` 만 잡으면 `HttpRequestMethodNotSupportedException`(ServletException 계열)이 그물을 빠져나간다. `ResponseEntityExceptionHandler` 를 상속해야 한다 |
| 파이썬 `round()` | **짝수로 맞춤**이다. `round(2.5)` 가 2 다. `Math.round` 는 3 이라 가격이 1원씩 어긋난다 — `common/Numbers` 가 `Math.rint` 로 맞춘다 |
| `grams` 의 정수/소수 | 파이썬은 `quantity` 가 정수면 `grams` 도 정수로 내보낸다 (`80` vs `625.0`) |
| 오라클 시간대 | 커넥션마다 `ALTER SESSION SET TIME_ZONE='+00:00'` 을 건다. 빼면 JDBC 가 JVM 기본 시간대(한국)를 세션 시간대로 잡아, 같은 표에 9시간 어긋난 행이 섞인다 |
| 좌표 | `NUMBER(9,6)` 을 `double` 로 받으면 37.5177 이 37.51769999… 로 떠서 응답 값이 달라진다. `BigDecimal` 로 받는다 |
| 오라클 `ROWNUM` | 정렬 **전에** 매겨진다. `ORDER BY` 를 안쪽에 두고 감싸지 않으면 최신 20건이 아니라 아무 20건이 나온다 |

### 게시판 · 공지는 스프링 쪽에도 501 로 세웠다

담당자가 파이썬 대신 스프링으로 만들기로 해서, 주소 20개 · DTO 13개 · 도메인 4개 ·

권한은 구현 전에도 걸린다. 게스트도 볼 수 있는 조회는 401 이 아니라 501 이고,

### 404 나 500 이 아니라 501 이다

주소와 요청/응답 스키마는 그대로 두고 **함수 안만 비워서 501 을 돌려준다.**

    routers/notices.py     5개
    services/post_service.py     만들 함수 목록만 남긴 명세 (37줄)
    services/notice_service.py   같음 (25줄)

404 면 "주소가 틀렸나" 가 되고 500 이면 "내가 뭘 잘못했나" 가 된다.
501 은 "아직 안 만들었다" 는 뜻이라 `/docs` 를 열어본 담당자에게 그대로
읽힌다. 문구도 "아직 만들지 않은 기능입니다. (게시판 담당자 작업 예정)"
로 적어뒀다.

## 쪼개 팔지 않는 재료는 최소단위로 사게 (STEP 42) (2026-09-14)

레시피는 "무 0.2개" 를 요구하는데 무를 0.2개 파는 가게는 없다. 환산까지만
하면 640원이 나오고, 계산은 맞지만 장바구니에는 못 담는다. 계란은 더
심해서 2개가 필요해도 KAMIS 는 30구 한 판으로 판다.

실제 레시피 데이터에 이런 재료가 **23종 112건** 있었다 (양파 0.5개 20건,
무 0.3개 19건, 배추 0.25포기 …).

### 전부 올리지는 않는다

판매 단위가 무게 · 부피면 저울로 달아 팔기 때문에 쪼갤 수 있다.

    무 0.2개       · 판매 1개    640원 ->  3,200원   올림
    계란 2개       · 판매 30구   466원 ->  7,000원   올림
    고춧가루 1큰술  · 판매 1kg    176원 ->    176원   그대로

무게 쪽까지 올리면 고춧가루 1큰술이 1kg(25,200원)이 되어, 애초에 환산이
없애려던 그 문제로 되돌아간다.

### 왜 큰지 밝혀야 한다

합계가 레시피 분량보다 커지므로, 이유를 적지 않으면 계산이 틀린 것처럼
읽힌다. 올림이 일어난 줄에 '최소단위' 배지와 "0.2개 필요 -> 1개 구입" 을
붙이고, 합계와 상세페이지 헤더에 몇 개가 그런지 적고, 표 아래에 최소단위
구입이 무엇인지 설명한다.

## 만드는 법을 자세하게 (STEP 40) (2026-09-13)

조리법마다 다섯 줄짜리 뼈대 하나를 돌려썼다. 그 뼈대가 쓰는 값은 첫 재료

    재료를 먹기 좋은 크기로 썬다.
    냄비에 물 400ml 를 붓고 센 불로 끓인다.
    돼지고기를 먼저 넣고 7분간 끓인다.
    나머지 재료를 넣고 5분 더 끓인다.

"나머지 재료" 라고 적는 순간 레시피가 아니라 빈칸이 된다. 어느 재료를
언제 넣는지가 레시피에서 알고 싶은 거의 전부다.

`integrations/steps.py` 로 옮기고 100종 평균 **10.2단계(8~13)** 로 늘렸다.

### 재료를 역할로 갈라 제 순서에 넣는다

주재료 · 오래 익는 것 · 향채 · 양념 · 고명으로 나눈다. 단단한 것이 먼저
들어가고 파는 마지막에 들어간다. 재료 66종마다 손질법을 따로 적고 분량도
같이 쓴다.

### 시간만으로는 모자라다

"7분간 끓인다" 만 있으면 불 세기도 모르고 제대로 됐는지도 모른다. 불
세기 · 시간 · 판단 기준을 같이 적는다. "국물이 재료 높이의 3분의 1쯤
남아 자작해지면 알맞다" 쪽이다.

### 태그가 너무 굵었다

'면' 한 장에 칼국수와 비빔국수가, '덮밥' 에 제육덮밥과 육회비빔밥이 같이

태그를 늘려 카탈로그 100종을 손보는 대신 **이름을 먼저 본다** — 비빔밥 ·
냉국 · 육회는 이름에 이미 답이 있다. 뼈대가 13가지로 갈렸다.

조사도 맞춘다. "300g" 은 "삼백그램" 이라 받침이 있고 "200ml" 는 없다.
글자 코드만 보면 둘 다 받침 없음이 되어 "300g를" 이 나온다.

## 시세 조사 대상이 아닌 재료를 밝힘 (STEP 39) (2026-09-13)

KAMIS 는 농수산물만 조사한다. 두부 · 밀가루 · 간장 같은 가공식품은 값이
아예 없어서 재료비 합계에서 조용히 빠지는데, 왜 적게 나오는지 화면에
적혀 있지 않았다.

### 값이 없는 이유가 두 가지다

    조사 대상 아님   가공식품. 앞으로도 값이 없다
    못 받았음        호출 제한이나 통신 오류. 잠시 뒤엔 나온다

전에는 표 아래에 "가공식품은 조사 대상이 아니라 가격이 없습니다" 한 줄을
합계가 모자랄 때마다 띄웠다. 호출 제한으로 값이 빈 날에도 그렇게 말하니
사실이 아니다.

`PriceItem.surveyed` 를 새로 뒀다. 품목표(`find_codes`)만 보고 정하므로
**API 가 죽어도 값이 흔들리지 않는다.**

### 가공식품이 원물 시세를 빌려 쓰고 있었다

부분일치가 이름 안에서 품목명을 찾는데, 가공식품은 재료 이름을 그대로
달고 있다.

    고추장   -> '고추' 시세
    배추김치 -> '배추' 시세
    깨소금   -> '소금' 시세

값이 틀리는 것도 문제지만, 상세페이지가 "이건 조사 대상이다" 라고 말하게
되는 게 더 나쁘다. `PROCESSED` 에 적힌 이름은 부분일치를 건너뛴다.

멸치액젓은 반대 방향이었다. 액젓은 실제 조사 품목인데 '멸치' 가 먼저
잡혀 멸치 시세가 붙었다(둘 다 두 글자라 길이로 못 가린다). 별칭으로
못박았다.

## 대시보드 추천을 쉬지 않고 흐르는 슬라이드로 (STEP 38) (2026-09-13)

다섯 장을 한 줄에 다 못 넣어 오른쪽이 비어 보였다. 페이지를 넘기는
방식은 넘어가는 순간 말고는 멈춰 있어서 빈 자리가 그대로 보인다.

목록을 두 벌 이어 붙이고 `-50%` 까지 밀어 되감는다. 절반을 밀면 두 번째
벌의 같은 자리가 와 있어서 이음매가 안 보인다.

### 간격을 `gap` 이 아니라 `margin-right` 로 준다

`gap` 은 카드 사이에만 들어가고 끝에는 안 붙는다. 그래서 전체 너비가
"카드 n장 + 간격 n-1개" 가 되고, `-50%` 가 간격 half 만큼 어긋나 이음매가
튄다. `margin-right` 는 마지막 카드 뒤에도 붙어 정확히 절반이 된다.

카드 너비는 `clamp()` 로 화면에 맞춘다. `flex-basis` 를 %로 주면 부모가
`width:max-content` 라 기준 너비가 없어서 한 장만 그려진다.

복제본은 `aria-hidden` · `inert` 로 빼서 읽는 장치와 탭 이동에 두 번
나오지 않게 했다.

## 찜하기를 DB로 옮김 (STEP 36) (2026-09-13)

찜 목록이 브라우저에만 있어서 로그아웃하면 사라졌다. 같은 계정으로 다른

## 날씨별 카탈로그 확충 (2026-09-13)

10월 중순 발표를 앞두고, **AI 가 붐벼도 화면이 비지 않도록** 카탈로그를
채웠다. 음식 39종 -> 99종.

### 왜 필요했나

Gemini 무료 등급이 자주 붐빈다(503). 실측으로 추천 44초 · 레시피 34초가
나왔고, 한 번은 46초를 쓰고 실패했다. 프론트는 30초에 끊는다.

그때 기대는 것이 카탈로그인데, 세어보니 날씨별 후보가 이랬다.

    국물 7종 · 얼큰 1종 · 튀김 1종

**비 오는 날에 밀어줄 것이 사실상 없었다.** 부침개 자리인 '튀김' 이 한 종
뿐이라, 비가 와도 매번 같은 국물 일곱 개가 돌아왔다.

### 15~24도에 규칙이 아예 없었다

작업 중에 드러난 것이다. `score_temperature` 가 이랬다.

    temp >= 25   더운 날 규칙
    temp < 15    추운 날 규칙
    그 사이       return 0      <- 빈칸

서울은 봄·가을이 통째로 이 구간이고, **10월 중순도 여기 들어간다.**
발표 당일에 날씨가 추천에 전혀 반영되지 않았을 것이다.

'선선한' 태그를 새로 만들고 규칙을 넣었다.

    '선선한' 이면          +3
    차게 먹는 것이면       -2      20도에 냉면이 1등으로 오르는 건 이르다

점수를 작게 준 이유가 있다. 이 구간에는 "반드시 이것" 이 없다. 더운 날의
냉면이나 추운 날의 국물 같은 강한 선호가 생기지 않는다. 크게 주면 Ban ·
냉장고 재료 같은 다른 조건을 덮어쓴다.

### 채운 결과

    태그          이전 -> 현재
    국물            7 -> 29
    얼큰            1 -> 10
    튀김            1 -> 17
    선선한           0 -> 28
    시원한음식       13 -> 23
    여름메뉴          7 -> 15

새로 넣은 60종은 네 묶음이다.

## 인증번호 재발송 제한 (2026-09-12)

비밀번호 재설정에서 인증번호를 **누르는 만큼 계속 보내고 있었다.** 이제
60초에 한 번만 나간다.

### 요청 한 번이 메일 한 통이다

이 엔드포인트는 다른 것과 성격이 다르다. 요청을 받으면 **바깥으로 메일을
내보낸다.** 간격이 없으면 두 가지가 생긴다.

    남의 주소를 넣고 연타       그 사람 받은편지함이 채워진다
    우리 쪽 발송 한도가 깎인다   개인 Gmail 은 하루 500통이다

STEP 32 에서 가입 여부를 알려주게 되면서 더 필요해졌다. 이제 send 를 연타해
주소 목록을 훑는 것도 가능해졌기 때문이다.

### 세는 표를 새로 만들지 않았다

`verification_codes.created_at` 이 곧 마지막 발송 시각이다. send 가 옛 코드를
지우고 하나만 새로 넣으므로, 가장 최근 행의 `created_at` 이 그 값이다.

메모리에 담아두는 방법도 있지만 서버를 다시 켜면 사라진다. **재시작만 하면
풀리는 제한은 없는 것과 비슷하다.**

### 왜 5분이 아니라 60초인가

"코드가 5분간 유효하니 5분 동안 못 누르게 하자" 가 처음 안이었다. 규칙이
하나로 단순해지고("살아있는 코드가 있으면 새로 안 준다"), 메일을 늦게 받아
코드가 이미 무효가 되는 일도 없어진다.

그런데 **메일이 안 오는 게 가장 흔한 실패다** — 스팸함, SMTP 일시 실패,
주소 오타. 그때 5분을 꼼짝없이 기다리게 된다. 비밀번호를 잊어버린 사람은
이미 곤란한 상태라 5분은 길다.

막으려는 것은 60초로 충분히 막힌다. 5분에 최대 5통이면 받은편지함을 채우는
데도, 하루 500통을 깎는 데도 쓸 수 없다.

`.env` 의 `OTP_RESEND_COOLDOWN_SECONDS` 한 줄이라 바꾸기 쉽게 빼뒀다.
**만료 시간(5분)보다 짧아야 한다** — 길면 코드가 만료된 뒤에도 새로 못 받아
아무것도 할 수 없는 구간이 생긴다.

### 남은 시간을 알려준다

"잠시 후 다시 시도하세요" 는 얼마나 기다려야 하는지 알려주지 않아서,
사용자가 10초마다 눌러보게 만든다. **막으려던 것을 오히려 부른다.**

    HTTP 429
    "인증번호를 방금 보냈습니다. 59초 후에 다시 요청해주세요."
    Retry-After: 59

`Retry-After` 는 429 에 붙이게 되어 있는 표준 헤더다. 화면이 문구에서 숫자를
긁어내지 않아도 된다. `api/client.js` 가 이 값을 `retryAfter` 로 넘겨준다.

### 화면은 버튼을 잠근다

문구로 말리는 것과 못 누르게 하는 것은 다르다. 남은 초를 1초마다 줄이면서
버튼에 그대로 적는다.

    [ 59초 후에 다시 받기 ]   <- disabled

### 429 는 아무것도 바꾸지 않는다

막으면서 옛 코드를 지워버리면, **메일은 안 왔는데 받아둔 코드도 못 쓰는**
상태가 된다. `raise_if_too_soon()` 을 지우기 전에 부르는 이유다.
테스트로 못 박았다.

### 검증

테스트 3건을 더했다 (213 -> 216).

    연달아 요청하면 막힌다                429 · 남은 시간 문구 · Retry-After 헤더
    막혔을 때는 코드가 새로 발급되지 않는다
    간격이 지나면 다시 받을 수 있다

마지막 것은 쿨다운을 잠깐 0 으로 낮춰 시간이 흐른 상황을 만든다. 실제로
60초를 기다리면 테스트 한 건이 1분을 잡아먹는다.

`raise_if_too_soon()` 호출을 주석 처리하고 돌려보니 첫 번째 한 건만 빨개졌다.

**216 통과 / 0 실패.**

## 가입되지 않은 이메일에 알려주기 (2026-09-12)

비밀번호 재설정에서 인증번호를 요청하면, 가입하지 않은 주소에도 "보냈습니다"
가 떴다. 이제 404 로 **가입되지 않은 회원입니다** 를 준다.

### 원래도 메일은 안 나갔다

먼저 확인한 것은 "가입 안 한 주소로 메일이 실제로 나가는가" 였다. 안 나간다.
`send_reset_code()` 첫 줄에서 `find_active_user()` 가 없으면 곧바로 돌아섰다.
DB 에 코드 행도 안 남는다.

    가입 안 된 주소   HTTP 200   메일 0회   OTP 0건   <- 화면만 "보냈습니다"
    가입된 주소       HTTP 200   메일 1회   OTP 1건

문제는 **응답이 글자 하나까지 같다**는 것이었다. 계정 열거를 막으려던 것이다.

### 왜 알려주는 쪽으로 바꿨나

두 가지다.

**오지 않는 메일을 기다리게 된다.** 오타를 쳐도 "5분 안에 입력해주세요" 가
뜬다. 사용자는 받은편지함과 스팸함을 뒤지다 5분을 보내고, 원인이 오타라는
것을 알 방법이 없다. 비밀번호를 잊어버린 사람은 이미 곤란한 상태다.

**이미 로그인에서 열려 있다.** `login_user()` 가 `(남은 시도 N회)` 를
**존재하는 계정에만** 붙인다. 없는 이메일과 응답을 비교하면 가입 여부를
알아낼 수 있다. 이 문서의 「왜 로그인 실패 시 남은 횟수를 알려주나」 에 그
트레이드오프가 이미 적혀 있다. 로그인이 열려 있는데 재설정만 가려봐야
실효가 없다.

즉 이번 변경은 새로 문을 연 것이 아니라, **두 곳의 정책을 맞춘 것**이다.

### 되돌리려면

`send_reset_code()` 의 `raise` 를 `return` 으로 바꾸면 된다. 다만 그때는
`login_user()` 의 401 문구도 같이 되돌려야 뜻이 있다. 한쪽만 닫으면 닫힌
것처럼 보이기만 한다.

### verify 는 그대로 둔다

`send` 에서 이미 알려주므로 숨길 것이 없어 보이지만, `verify` 의 400 문구는
"틀린 코드" · "만료된 코드" · "없는 요청" 을 **하나로 통일**한 것이다.
어느 쪽인지 구분해 알려주면 공격자가 유효한 코드를 좁혀나가는 데 쓸 수 있다.
가입 여부와는 다른 이야기라 건드리지 않았다.

### 탈퇴 회원도 같이 걸린다

`find_active_user()` 가 `use_yn='Y'` 만 찾는다. 탈퇴한 사람에게 재설정 메일을
보낼 이유가 없고, 화면에는 "가입되지 않은 회원" 으로 보이는 편이 맞다.

### 화면은 손대지 않았다

`PasswordResetPage` 가 이미 `catch` 에서 에러를 띄우고 단계를 넘기지 않는다.
404 가 오면 1단계에 머문 채 "가입되지 않은 회원입니다" 가 뜬다.

### 검증

이 엔드포인트에는 **테스트가 하나도 없었다.** 5건을 새로 넣었다.

    가입되지 않은 이메일에는 인증번호를 안 보낸다     404
    가입된 이메일에는 인증번호를 보낸다               200 + DB 에 코드 1건
    인증번호를 다시 받으면 옛 코드는 버려진다         여러 개 살아있으면 안 된다
    틀린 인증번호는 거부된다                          400
    가입되지 않은 이메일의 인증 확인도 거부된다       verify 는 구분하지 않는다

"가입된 이메일에는 보낸다" 는 DB 를 직접 본다. 200 만 확인하면 메일을 안
보내도 통과해버리는데, 그게 바로 이 테스트가 잡아야 하는 경우다.

`raise` 를 `return` 으로 되돌려 돌려보니 첫 번째 한 건만 빨개졌다.

## 히스토리 · 공지 페이징 (2026-09-12)

게시판에만 있던 페이징을 나머지 두 목록에도 붙였다. 이제 목록 셋이 같은
모양으로 온다.

### 세 번째로 같은 코드를 쓰게 됐다

STEP 28 에서 `PostPage` 를 만들 때는 한 벌이라 그 자리에 뒀다. 이번에
히스토리와 공지가 붙으면서 **같은 네 칸(total · page · size · total_pages)을
세 번 적게 됐다.** 그래서 `schemas/page.py` 로 옮겼다.

    class Page(BaseModel):       total · page · size · total_pages
    class PostPage(Page):        items: list[PostListItem]
    class MealHistoryPage(Page): items: list[MealHistoryResponse]
    class NoticePage(Page):      items: list[NoticeResponse]

`Page[T]` 제네릭을 쓰지 않았다. Pydantic 제네릭은 /docs 의 스키마 이름이
`Page_PostListItem_` 처럼 나온다. 읽는 사람이 늘어나는 문서에서 이름이 기계가
지은 것처럼 보이는 건 손해다. 상속으로 두면 `PostPage` 라는 이름이 그대로 남는다.

`DEFAULT_PAGE_SIZE` 와 `MAX_PAGE_SIZE` 도 같이 옮겼다. 전에는 앞의 것이
`post_service`, 뒤의 것이 `routers/posts` 에 흩어져 있었다. 올림 계산도
`count_pages()` 하나로 모았다 — 세 곳에 `(total + size - 1) // size` 를 적으면
한 곳만 고쳐질 때 페이지 수가 서로 달라진다.

### 화면에서 거르던 것이 깨진다

글쓰기 화면은 "아직 공유하지 않은 기록" 만 고르게 한다. 전에는 전체를 받아
화면에서 걸렀다.

    const sharable = histories.filter((h) => !h.shared_post_id)

기록에 페이징이 붙으면 이게 **조용히 깨진다.** 1페이지 20건이 전부 공유된
기록이면 고를 것이 하나도 없는 화면이 된다. 기록이 21건 이상인 사람에게만
생기는 일이라 더 늦게 발견된다.

그래서 서버가 거르게 했다.

    GET /api/histories?shared=false   아직 공유 안 한 것만
    GET /api/histories?shared=true    이미 공유한 것만
    GET /api/histories                전부 (기록 화면)

COUNT 와 목록이 같은 OUTER JOIN 을 봐야 한다. 한쪽에만 붙이면 "3페이지가
있다는데 열면 비어 있는" 일이 생긴다.

글쓰기 화면은 `size=50` 으로 받는다. 드롭다운이라 한 번에 다 보여줘야 하는데,
수백 개짜리 드롭다운이 쓸 만한 것도 아니라서 최신 50건이면 충분하다.
사람은 보통 방금 먹은 것을 공유한다.

### 요약줄이 한 페이지만 세고 있었다

History 화면 위쪽의 "총 N건 · 누적 M원" 을 화면이 직접 세고 있었다.

    let totalCost = 0
    for (const history of histories) totalCost += history.estimated_cost ?? 0

페이징이 붙으면 `histories` 가 한 페이지 몫뿐이라 **"총 20건" 에서 멈춘다.**
`GET /api/histories/stats` 가 이미 전체를 세어주고 있어서 그걸 쓰게 바꿨다.
화면이 가진 배열로 전체를 세는 코드는 페이징이 붙는 순간 전부 이런 문제가 된다.

### 지울 때 그 페이지를 다시 받아온다

전에는 배열에서 그 줄만 뺐다. 페이징이 붙으면 **19건짜리 페이지**가 되고,
뒷 페이지의 첫 기록이 당겨져 오지 않아 어느 페이지에도 안 나온다.
마지막 한 건을 지워 페이지가 통째로 사라지면 한 장 앞으로 보낸다.

### 고정 공지는 1페이지에만 보인다

정렬이 `pinned_yn DESC` 먼저라 고정은 전부 앞쪽에 몰린다. 2페이지로 넘어가면
사라지는데, 그게 맞다 — 고정은 "목록의 맨 위" 라는 뜻이지 "모든 페이지의
맨 위" 가 아니다. 페이지마다 따라다니면 2페이지의 절반이 이미 읽은 공지가 된다.

새 공지를 쓰면 1페이지로 돌려보낸다. 3페이지를 보다가 공지를 쓰면 저장은 됐는데
화면에는 안 보이는 상태가 되기 때문이다. 수정은 그 공지가 있던 페이지에 남는다.

공지 페이지 번호는 게시판과 따로 센다. 게시판 3페이지를 보다 공지 탭으로
옮겼는데 공지도 3페이지면 이상하다.

### 공지는 왜 지금 붙였나

공지는 네 건뿐이라 페이징이 없어도 돌아간다. 그래도 붙인 이유는 공지가
**사용자 수가 아니라 운영 기간에 비례해 늘어나는** 값이기 때문이다. 점검 ·
이벤트 안내가 한 달에 몇 건씩 쌓이면 몇 년 뒤에는 수백 건이 된다.

그때가 게시판보다 더 나쁘다. 화면이 목록에서 그 자리에 펼치느라 본문(CLOB)을
같이 싣고 있어서, 게시판 목록보다 한 건당 무겁다.

### 검증

통합 테스트가 200건 -> 208건이 됐다. 새로 8건이다.

    공지 한 페이지 크기를 줄이면 그만큼만 온다

## 회원 권한 등급과 공지 작성 (2026-09-12)

공지를 DB 에 직접 넣던 것을 화면에서 쓸 수 있게 했다. STEP 27 에서 "관리자
구분 컬럼이 없어서 쓰기 API 를 만들지 않는다" 고 미뤄둔 것이 이 작업이다.

### 등급을 숫자 한 칸으로

`USERS.USER_LEVEL` 을 넣었다. 1 이 관리자, 2 가 일반 회원이다.

    ALTER TABLE users ADD (user_level NUMBER(1) DEFAULT 2 NOT NULL);
    CONSTRAINT ck_users_user_level CHECK (user_level IN (1, 2))

**DEFAULT 를 2 로 둔 이유.** 빠뜨렸을 때 일반 회원이 되는 쪽이 안전하다.
`DEFAULT 1` 이면 이 컬럼을 모르는 INSERT 하나가 관리자를 만들어낸다.
회원가입 코드는 이 컬럼을 아예 건드리지 않는다.

**CHECK 를 건 이유.** 바로 옆의 `NOTICES.CATEGORY` 에는 일부러 안 걸었다 —
분류는 운영하면서 늘어나는 값이라, 늘 때마다 DDL 을 고쳐야 하는 제약은 득보다
실이 크다. 등급은 반대다. "관리자냐 아니냐" 두 갈래라 늘어날 여지가 없고,
오타로 0 이나 3 이 들어가면 관리자 판정이 조용히 어긋난다.

**관리자를 만드는 화면도 API 도 두지 않았다.** 아무나 자기를 관리자로 올릴
수 있으면 등급이 의미가 없다. `db/06_add_user_level.sql` 아래쪽에 계정 하나를
올리는 UPDATE 를 적어뒀다.

### '요리 레벨' 과 헷갈리는 이름

이 앱에는 이미 레벨이 있다. 마이페이지의 요리 레벨(1 → 2 → 3 …)인데,
식사 기록 · 후기로 쌓인 경험치에서 `make_level()` 이 매번 계산하는 값이고
DB 에 저장하지 않는다. **둘은 아무 상관이 없다.**

이름만 보고 `user_level` 을 요리 레벨로 읽으면 "레벨 2 회원" 이 관리자보다
높아 보인다. DDL 주석 · 모델 주석 · 마이그레이션 파일 세 곳에 다 적어뒀다.

코드에서는 숫자를 그대로 쓰지 않는다.

    USER_LEVEL_ADMIN = 1
    USER_LEVEL_MEMBER = 2

    user.is_admin        # models/user.py 의 프로퍼티

`if user.user_level == 1` 은 읽는 사람이 1 이 관리자인지 알 수 없고,
반대로 적어도 눈에 띄지 않는다.

### 등급 검사는 한 군데서만

`get_admin_user` 의존성 하나를 만들고 세 엔드포인트가 그걸 받는다.

    POST   /api/notices          공지 작성
    PUT    /api/notices/{id}     공지 수정
    DELETE /api/notices/{id}     공지 삭제

`get_current_user` 를 `Depends` 로 받아서 그 위에 등급 한 줄만 더 본다.
토큰 검사 · 탈퇴 확인 · 계정 잠금은 이미 거기서 다 한다. 덕분에 로그인하지
않았으면 403 이 아니라 **401 이 먼저** 나간다 — 맞는 순서다. "누구인지
모르겠다(401)" 와 "누구인지는 알지만 권한이 없다(403)" 는 다른 말이다.

서비스 계층에서는 등급을 다시 보지 않는다. 같은 검사를 두 군데서 하면
한쪽만 고쳐질 때 조용히 어긋난다.

### 403 이다, 404 가 아니다

게시판의 '남의 글 수정' 은 404 로 돌려준다. 403 을 주면 "그 번호의 글은
존재한다" 는 사실이 새어나가기 때문이다.

공지는 그 걱정이 없다. **목록이 Guest 에게도 통째로 열려 있어서** 몇 번
공지가 있는지는 이미 공개된 정보다. 숨길 것이 없으면 사실대로 알려주는
편이 낫다 — 404 로 받으면 화면이 "없는 공지" 라고 잘못 안내하게 된다.

### '내 공지' 라는 개념이 없다

게시판은 내 글만 고칠 수 있다. 공지는 **관리자면 누가 쓴 공지든** 고치고
지운다. 공지는 개인의 글이 아니라 운영팀이 서비스 이름으로 내는 글이라,
쓴 사람이 자리를 비웠다고 아무도 못 고치면 곤란하다. 화면도 작성자를
'뭐먹지? 운영팀' 하나로만 보여준다.

같은 이유로 수정할 때 `user_id` 를 건드리지 않는다. 처음 쓴 사람이 누구였는지는
기록이고, 고쳤다고 바뀌는 값이 아니다.

**조회수도 그대로 둔다.** 오타 하나 고쳤다고 "이 공지를 몇 명이 읽었나" 가
0 으로 돌아가면 안 된다. 작성 요청에서도 `view_count` 를 받지 않는다 —
읽혀서 쌓이는 값이지 쓰는 사람이 정하는 값이 아니다.

### 작성자를 본문으로 받지 않는다

`user_id` 는 토큰에서 나온 사람으로 서버가 넣는다. 본문으로 받으면 남의
이름으로 공지를 쓸 수 있게 된다. 게시판이 `meal_history_id` 만 받고 레시피를
직접 복사해 넣는 것과 같은 규칙이다 — **클라이언트가 보낸 값을 믿지 않는다.**

### 화면 — 버튼을 숨기는 것은 잠그는 것이 아니다

`UserResponse` 에 `is_admin` 을 더했다. 로그인 응답과 `/api/auth/me` 가 같은
스키마를 쓰므로, `AuthContext` 의 `user` 에 바로 실려온다.

**등급 숫자를 그대로 내리지 않는다.** 화면이 필요한 건 "공지 쓰기 버튼을
그릴까" 하나뿐이라, 1 이 관리자라는 규칙까지 프론트에 퍼뜨릴 이유가 없다.

이 값은 그릴지 말지에만 쓴다. 진짜 차단은 서버가 한다 — 콘솔에서
`createNotice()` 를 직접 불러도 403 이다.

### 폼은 페이지가 아니라 그 자리에 편다

게시글은 `/community/write` 페이지가 따로 있다. 공유할 기록을 고르고, 사진을
붙이고, 본문이 길어서 화면이 하나 필요하다.

공지는 항목이 넷뿐이다(제목 · 분류 · 고정 · 본문). 목록 위에 펴면 방금 쓴
공지가 어디에 끼는지 바로 보이고, 취소해도 돌아올 곳이 없다.
`NoticeList` 가 상세 페이지 없이 그 자리에서 펼치는 것과 같은 결이다.

작성과 수정을 한 컴포넌트로 뒀다. 입력칸이 넷으로 똑같고, 다른 건 "처음
값이 비어 있나 채워져 있나" 와 "POST 냐 PUT 이냐" 둘뿐이다.

    editing === null     폼이 닫혀 있다
    editing === 'new'    새 공지
    editing === {...}    그 공지를 수정하는 중

열렸는지와 무엇을 고치는지를 state 두 개로 두면 어긋난 조합(열렸는데 대상이
없다)이 생긴다. 하나로 두면 그럴 수가 없다.

`NoticeForm` 에 `key` 를 대상마다 다르게 준다. 안 주면 **'수정' 을 눌러 다른
공지로 갈아탈 때 입력값이 그대로 남는다** — `useState` 초기값은 첫 렌더에서만
쓰이기 때문이다.

### 수정 · 삭제 버튼은 펼친 본문 아래에

제목 줄 전체가 이미 아코디언 토글 `<button>` 이다. 그 안에 버튼을 또 넣으면
HTML 상 중첩 버튼이 되어 브라우저마다 다르게 동작한다.

자리가 밀려서 내린 것이지만 결과적으로도 낫다. 삭제는 되돌리기 번거로운
동작이라, 내용을 펼쳐 확인한 뒤에 누르는 자리에 있는 편이 맞다.

### 저장한 뒤 목록을 다시 받아온다

응답으로 온 공지를 화면의 배열에 직접 끼워 넣지 않는다. **고정을 켜면 맨
위로 가야 하는데 그 정렬은 서버 규칙이다.** 화면이 흉내 내면 새로고침한
순간 순서가 달라진다. 공지는 몇 건뿐이라 다시 받아도 부담이 없다.

### 테스트 뒷정리에 한 줄이 필요해졌다

`conftest.py` 의 `CLEANUP_SQL` 에 `DELETE FROM notices WHERE user_id = :uid`
를 더했다. 없으면 그 다음 줄의 `DELETE FROM users` 가 **ORA-02292** 로 막힌다.

`fk_notices_user` 에는 `ON DELETE CASCADE` 가 없다. 운영자 계정이 사라진다고
공지가 같이 사라지면 안 되기 때문인데(`models/notice.py`), 그래서 테스트가
만든 공지는 손으로 지워야 한다. `user_id` 로 좁히는 것이 중요하다 — 조건
없이 지우면 시드해둔 진짜 공지가 같이 날아간다.

### 검증

통합 테스트가 185건 -> 197건이 됐다. 새로 12건이다.

    로그인 없이는 공지를 못 쓴다              403 이 아니라 401
    일반 회원은 공지를 못 쓴다                404 가 아니라 403
    일반 회원은 is_admin 이 거짓이다
    관리자는 공지를 쓴다                      조회수는 0 에서 시작한다
    관리자는 is_admin 이 참이다
    분류를 안 적으면 '안내' 다                고정도 기본이 꺼짐
    공백만 든 제목은 거른다                   min_length=1 을 통과하는 값
    고정한 공지가 목록 맨 위에 온다

## 비 오는 날 추천 (2026-09-11)

날씨를 받아오기만 하고 점수에 안 쓰던 것을 연결했다. **28도 장마날에 냉면이
1등으로 올라오던 것**이 이 작업의 출발점이다.

### 어디가 비어 있었나

`condition` 은 이미 다 흐르고 있었다.

    weather_api      CLEAR / CLOUDS / RAIN / SNOW 를 만들어 내려준다   ✅
    AI 프롬프트      "오늘 날씨: ... 비 25도" 로 넣고 있었다            ✅
    화면             비 배경 · 🌧️ 이모지를 이미 그리고 있었다           ✅
    score_weather()  temp 만 읽고 condition 을 안 봤다                  ❌

빠진 곳은 **점수 계산 한 군데**였다. 그래서 진짜 AI(gemini)를 쓸 때는 비가
반영됐고, mock 이나 AI 가 죽어 카탈로그로 떨어질 때만 안 됐다.
"가끔 되는" 상태가 제일 찾기 어렵다.

### 기온과 하늘을 따로 재서 더한다

    score_weather = score_temperature(temp) + score_sky(condition)

둘은 서로 독립이다 — 장마철에는 28도인데 비가 오고, 12월에는 5도인데 맑다.
한쪽이 다른 쪽을 덮어쓰지 않고 더하기만 한다.

    눈 오는 추운 날의 국물   +6 +7 = +13   같은 방향이면 더 세게
    비 오는 더운 날의 냉면   +8 -5 =  +3   반대면 서로 깎는다

`score_weather()` 를 지우지 않고 남긴 이유는 부르는 쪽(`score_food`)이
날씨 딕셔너리 하나만 넘기면 되게 하기 위해서다. 안을 둘로 나눈 것뿐이다.

### 점수

    SNOW   국물 +7             찬 음식 -8
    CLEAR · CLOUDS · 모르는 코드 · None   전부 0

비에 튀김을 넣은 건 부침개 자리다. 기온만 보면 절대 안 올라온다.

눈을 더 세게 준 이유는 기온 점수와 겹치기 때문이다. 겹치는 쪽으로 확실히
밀어주는 편이 맞다 — 눈 오는 날 냉면을 추천받고 싶은 사람은 없다.

## 게시판 페이징 (2026-09-11)

목록을 한 번에 다 내려주던 것을 20건씩 끊었다. 글이 수백 건이 되면 CLOB 은
안 실어도 본문 미리보기 · 좋아요 · 댓글 수를 전부 세어 내려주게 된다.

### 응답을 한 겹 감쌌다

    전:  [ {...}, {...} ]
    후:  { items: [...], total: 137, page: 3, size: 20, total_pages: 7 }

화면이 "3 / 7" 을 그리려면 **전체가 몇 건인지** 알아야 한다. 20건짜리 배열만
와서는 이게 마지막 페이지인지 알 방법이 없다. 개수를 응답 헤더에 담는 방법도
있지만, 본문에 같이 두면 `/docs` 에도 보이고 프론트도 `data.total` 로 그냥
읽는다.

목록 응답 모양이 바뀌었으므로 `getPosts` 를 쓰는 쪽(`CommunityPage`)과
기존 테스트 2건도 같이 고쳤다.

### COUNT 와 목록이 같은 조건을 봐야 한다

쿼리가 두 번 나간다 — 전체 건수를 세는 COUNT 와, 이 페이지 몫을 읽는 목록.
**한쪽에만 검색어를 붙이면** "7페이지가 있다" 고 해놓고 열면 비어 있는 화면이
된다. JOIN 도 양쪽을 맞춰뒀다.

한 번에 다 읽어서 파이썬에서 잘라도 결과는 같지만, 그러면 천 건을 읽어놓고
20건만 쓰게 된다. 자르는 일은 DB 가 해야 한다.

### 정렬에 id 를 같이 넣은 이유

`created_at` 만으로 정렬하면 시각이 같은 글 둘의 순서를 DB 가 마음대로
정한다. 페이지를 넘길 때마다 순서가 달라지면 **같은 글이 1페이지와 2페이지에
다 나오거나, 어느 페이지에도 안 나온다.** id 는 겹치지 않으므로 순서가 항상
똑같이 정해진다.

원래도 `.order_by(created_at.desc(), id.desc())` 로 되어 있었다. 페이징이
없을 때는 없어도 티가 안 나던 것이 이제 필요해진 것이다.

### 좋아요 · 댓글 수를 페이지 몫만 센다

`count_likes_by_post()` 가 인자로 `post_ids` 를 받게 바꿨다. 없으면 1페이지
20건을 보여주려고 전체 글의 좋아요를 다 세게 된다. 이제 글이 수천 건이 돼도
세는 양이 20건어치로 고정된다.

(Oracle 의 `IN` 은 1000개가 상한이다. `size` 상한이 50 이라 걸릴 일이 없다.)

### size 에 상한을 뒀다

`?size=100000` 한 번으로 글 전체를 끌어올 수 있으면 페이징을 붙여놓고
우회로를 열어두는 셈이다. 50 을 넘으면 422 다.

범위를 벗어난 `page` 는 404 가 아니라 **빈 items** 다. 9999 페이지를 열었다고
에러 화면이 될 일은 아니고, 화면이 `total_pages` 를 보고 되돌리면 된다.

### 검색어를 state 두 개로 나눴다

    keyword   입력칸에 지금 찍혀 있는 글자
    query     실제로 서버에 보낸 검색어 (타이핑이 멎고 0.3초 뒤에 따라온다)

전에는 하나였고 `getPosts` 호출 자체를 `setTimeout` 으로 감싸고 있었다.
페이징이 붙으면서 **페이지 버튼을 눌러도 0.3초를 기다리게** 되어버려서,
기다리는 것(검색어)과 즉시 나가는 것(페이지)을 갈랐다. effect 도 둘로 나뉘어
각자 하는 일이 하나씩이다.

검색어가 바뀌면 `page` 를 1 로 되돌린다. 3페이지를 보다가 검색하면 결과가
2건인데 3페이지를 달라고 해서 빈 화면이 뜬다.

"검색 결과가 없습니다" 문구도 `keyword` 가 아니라 `query` 를 본다. 타이핑
도중에는 아직 이전 결과가 떠 있는데, `keyword` 로 판단하면 목록보다 문구가
먼저 바뀐다.

### 새로 생긴 것

    backend/app/schemas/post.py       PostPage
    frontend/src/components/common/Pagination.jsx
    frontend/src/styles/components/common/Pagination.css

`Pagination` 은 현재 페이지 둘레로 ±2 개만 그리고 나머지는 `…` 로 접는다.
글이 2000건이면 페이지가 100개인데 다 그리면 버튼이 화면을 덮는다. 첫 페이지와
끝 페이지는 항상 남긴다 — 100페이지에서 1페이지로 한 번에 갈 길이 필요하다.

**딱 한 칸만 비면 `…` 대신 그 번호를 그대로 쓴다.** `…` 도 한 칸을 차지해서,
접어봐야 좁아지지 않는데 클릭만 못 하게 된다.

    page=1  total=100  ->  1 2 3 … 100
    page=3  total=100  ->  1 2 3 4 5 … 100
    page=50 total=100  ->  1 … 48 49 50 51 52 … 100

### 검증

통합 테스트가 169건 -> 175건이 됐다. 새로 6건이다.

## 공지사항과 미니게임 기록 (2026-09-10)

테이블 두 개(`NOTICES` · `GAME_HISTORIES`)가 DDL 에만 있고 백엔드가 쓰지
않던 것을 실제로 연결했다. 이로써 표 9개를 전부 쓴다.

### 공지를 파일에서 DB 로

`catalog.json` 에 다섯 건이 하드코딩돼 있었다. 카테고리 칩·룰렛 조각과
한 묶음으로 "사용자가 만들지 않는 목록" 취급을 한 것인데, **성격이 다르다.**

    카테고리 칩   개발자가 정한다. 바뀌면 코드도 같이 바뀐다
    공지사항      운영자가 계속 새로 쓴다. 코드와 무관하다

파일에 두면 공지 하나 올릴 때마다 서버를 다시 배포해야 한다. 그래서
`NOTICES` 표로 옮겼고, 주소도 `/api/catalog/notices` → `/api/notices` 로
옮겼다. 있던 다섯 건은 `db/05_seed_notices.sql` 로 옮겼다.

**`CATEGORY` 컬럼을 하나 추가했다.** 화면(`NoticeList.jsx`)이 '점검' ·
'안내' · '업데이트' 배지를 이미 그리고 있었는데 표에 자리가 없었다.
없이 옮기면 배지가 빈칸이 된다.

CHECK 는 걸지 않았다. 분류는 운영하면서 늘어나는 값이고, 늘 때마다 DDL 을
고쳐야 하는 제약은 득보다 실이 크다. 화면도 '점검'만 경고색이고 나머지는
기본색이라 모르는 값이 와도 깨지지 않는다.

**쓰기 API 는 만들지 않았다.** `USERS` 에 관리자 구분 컬럼이 없어서
"운영자만 작성"을 가릴 방법이 없다. 로그인만 하면 아무나 공지를 쓸 수 있는
API 를 두느니, 지금은 DB 에 직접 넣는 편이 낫다.

> 2026-09-12 에 풀렸다. `USERS.USER_LEVEL` 이 생기면서 "관리자만" 을 가릴 수
> 있게 됐다 — 아래 「회원 권한 등급과 공지 작성」 참고.

조회수는 목록 GET 에서 올리지 않는다. 화면을 열 때마다 다섯 건이 한꺼번에
오르면 숫자가 뜻을 잃는다. 공지를 펼칠 때 `POST /api/notices/{id}/view` 를
부른다 — 게시판의 `/view` 와 같은 방식이다.

### 게임 종류를 A · B · C 로

`ck_game_histories_type` 이 `'A'` 하나만 허용했는데 화면의 게임은 셋이다.

    A  음식 월드컵   (/game/worldcup)   후보를 둘씩 비교해 좁힌다
    B  취향 밸런스   (/game/balance)    질문 다섯 개로 조건을 만든다
    C  랜덤 돌림판   (/roulette)        운에 맡긴다

글자와 게임의 대응은 `services/game_service.py` 의 `GAME_TYPES` 한 곳에만
적었다. DB 에는 글자만 넣는다 — 표가 '누가 · 무엇을 · 언제'만 남기는
로그라 종류 이름까지 매 행에 넣을 이유가 없다.

**끝난 판이 아니라 시작한 판을 센다.** 세 게임 모두 도중에 나가는 일이
흔하다(월드컵은 일곱 번, 밸런스는 질문 다섯 개를 지나야 끝난다). 끝난 것만
세면 "이 게임을 얼마나 열어보는가"를 알 수 없는데, 지금 알고 싶은 건 그쪽이다.

### 이 표만 모델이 클래스가 아니다

`GAME_HISTORIES` 는 `class X(Base)` 가 아니라 SQLAlchemy Core 의 `Table` 이다.

선언형 모델은 PK 를 반드시 요구한다. "이 객체가 DB 의 어느 행인지"를 PK 로
따라다니기 때문이다. 그런데 이 표에는 PK 가 없다 — 수정도 삭제도 하지 않는
누적 로그라 행 하나를 지목할 일이 없어서 일부러 뺐다.

억지로 `(user_id, created_at)` 을 PK 라고 적어두면 DDL 에 없는 제약을
코드에만 적는 셈이고, 같은 회원이 같은 순간에 두 번 기록되면 SQLAlchemy 가
두 행을 하나로 착각한다. 필요한 건 INSERT 하나뿐이라 객체로 다룰 이유도 없다.

### StrictMode 가 기록을 두 배로 만들던 것

게임 페이지 세 곳이 `useGamePlayLog(gameKey)` 훅 하나를 부른다. 그 안에서

> 이 훅은 2026-09-18 「소스 단계 낮추기」에서 지웠다. 지금은 게임 화면
> 세 곳이 각자 `postGamePlay` 를 부른다. 아래는 당시 기록이다.

`useRef` 로 한 번만 보내게 막았다.

React 18 이후 개발 모드는 effect 를 일부러 두 번 실행한다. 그대로 두면
개발 중에 게임 기록이 매번 두 줄씩 쌓여서, 실제 사용자 수가 두 배로 보이는
통계가 된다.

기록 실패는 조용히 넘어간다. 놀러 온 사람에게 서버 사정을 알릴 이유가 없다.

## 후기 첨부파일 (2026-09-10)

후기에 사진 한 장을 붙일 수 있게 했다. DDL 과 모델은 이미 와 있었고
(`8219edd`), 그 위에 나머지 계층을 얹었다.

### 왜 글쓰기 API 를 안 건드렸나

파일을 붙이는 방법이 두 가지였다.

    A  POST /api/posts 를 multipart 로 바꿔 글과 파일을 한 번에 받는다
    B  POST /api/posts/{id}/file 을 따로 두고 두 번 부른다

**B 를 골랐다.** A 는 요청이 한 번이라 원자적이지만, FastAPI 는 한
엔드포인트에서 `UploadFile` 과 Pydantic 본문을 같이 못 받는다. 필드를
`Form(...)` 으로 풀어써야 하고, 그러면 `PostCreateRequest` 의 검증기
(공백만 든 제목·본문 차단)가 안 돈다. 수정 쪽에도 "파일 유지 / 교체 /
삭제" 를 구분하는 플래그가 붙는다.

B 의 단점인 "중간 상태"는 이 서비스에서 문제가 아니다. 업로드가 실패해도
남는 건 `file_yn='N'` 인 **첨부 없는 멀쩡한 글**이고, 첨부는 원래 선택
사항이라 그게 정상 상태다. 상세 화면에서 사진만 다시 올리면 된다.

덤으로 상세에서 사진만 갈아 끼우는 기능이 공짜로 생겼다.

### 왜 uploads 폴더를 정적 서빙하지 않나

`app.mount("/uploads", StaticFiles(...))` 두 줄이면 끝나는데 안 썼다.

- **삭제된 글의 사진이 계속 열린다.** 정적 서빙은 URL 만 알면 그만이라
  `use_yn='N'` 을 볼 방법이 없다. 지금은 `open_post_file()` 이 살아있는
  글인지 먼저 확인한다
- **원본 파일명을 못 준다.** 디스크에는 UUID 로 저장돼 있어서 그대로
  주면 `a1b2c3....jpg` 가 내려간다. 지금은 `file_org_name` 으로
  "김치찌개.jpg" 를 돌려준다

`attachment` 가 아니라 `inline` 으로 준다. attachment 로 주면 `<img>` 에
넣었을 때 안 그려지고 내려받기 창이 뜬다.

### 파일 이름을 바꿔서 저장하는 이유

사용자가 올린 이름을 그대로 쓰면 두 가지가 깨진다. DDL 주석이 짚어둔 그대로다.

    같은 이름끼리 덮어쓴다     "사진.jpg" 를 두 사람이 올리면 하나가 사라진다
    경로가 섞여 들어온다       "../../.env" 면 서버 파일을 건드린다

그래서 저장은 UUID 로 하고 원래 이름은 보여주기용으로만 따로 적는다.
`absolute_path()` 가 만들어진 경로를 한 번 더 검사한다 — 지금은 경로도
파일명도 서버가 지어낸 값이라 밖으로 나갈 수 없지만, DB 값을 그대로 믿고
파일을 열어주는 코드는 언젠가 반드시 사고가 난다.

### 컬럼 여섯 개를 손으로 만지지 않는다

`ck_reviews_file_set` 이 `file_yn` 과 나머지 다섯 컬럼을 묶어서 본다.
첨부를 뗄 때 `file_yn` 만 'N' 으로 바꾸고 경로를 남겨두면 ORA-02290 이 난다.
그래서 서비스는 모델의 `set_file()` · `clear_file()` 만 부른다.

### 순서에 뜻이 있다

교체할 때는 **새 파일 저장 → DB commit → 옛 파일 삭제** 다.
옛 파일을 먼저 지우면 commit 이 실패했을 때 DB 는 옛 파일을 가리키는데
디스크에는 없다 — 화면에 깨진 이미지가 뜬다.

글을 논리 삭제할 때는 **파일을 안 지운다.** 되살릴 수 있어야 하는데
파일을 지우면 글만 돌아온다.

### 새로 생긴 것

| 계층 | 파일 | 하는 일 |
|---|---|---|

## 주소로 날씨 보기 (2026-09-09)

회원가입에서 받은 주소가 **저장만 되고 쓰이지 않던 것**을 실제로 연결했다.
화면에는 "사는 곳을 적어두면 그 지역 날씨로 추천해드립니다" 라고 적어놓고
동작은 안 하던 상태였다.

### 좌표를 미리 구워뒀다

"서울특별시 강남구" 를 좌표로 바꾸는 건 바깥 API(Nominatim) 일이고 2~3초 걸린다.
가입할 때마다 부르면 회원가입이 그만큼 느려지고, 그 API 가 죽으면 가입이 막힌다.

그런데 시·군·구는 **목록이 고정이고 좌표도 변하지 않는다.**
그래서 일회성 스크립트로 267개를 한 번만 변환해 `app/data/regions.json` 에
넣어뒀다. 서비스가 돌 때는 표에서 찾기만 한다.

    scratchpad/build_regions.py  ->  regions.json  (저장소에 커밋)

부수 효과가 하나 더 있다. **좌표 변환이 실패한 항목은 지명을 잘못 적었다는 뜻**이라,
목록을 만드는 과정이 곧 검증이 됐다.

### 주소를 드롭다운으로 바꿨다

전에는 시·도 · 시·군·구가 자유 입력이었다. 그러면 `서울시` / `서울특별시` /
`서울` 이 뒤섞이고, **그중 어느 것도 좌표로 바꾸지 못한다.**
목록에서 고르게 하니 이 문제가 사라졌다.

`AddressPicker` 컴포넌트 하나를 회원가입과 마이페이지가 같이 쓴다.
따로 만들면 한쪽만 고쳤을 때 가입 때 고른 주소를 수정 화면에서 못 고르게 된다.

시·도를 바꾸면 시·군·구를 **반드시 비운다.** 안 비우면 "부산광역시 강남구" 같은
있지도 않은 조합이 만들어지고, 서버는 좌표를 못 찾아 기본 좌표로 떨어진다.

### 좌표는 클라이언트가 못 보낸다

`RegisterRequest` · `ProfileUpdateRequest` 에서 `latitude` / `longitude` 를 뺐다.
주소를 받아 **서버가** 좌표로 바꾼다. 클라이언트가 좌표를 직접 보내게 두면
주소와 좌표가 어긋난 회원이 생긴다.

주소를 지우면 좌표도 지운다. 안 그러면 이사한 뒤에도 화면에는 부산이라고
적혀 있는데 서울 날씨가 나온다.

### 날씨 좌표 우선순위

    1) 브라우저가 준 위치        지금 있는 곳이 가장 정확하다
    2) 회원가입 때 고른 주소     위치 권한을 거부했거나 지원 안 하는 브라우저
    3) 기본 좌표(종로2가)        로그인 안 했고 위치도 없을 때

2번이 없던 게 원래 문제였다. 위치 권한을 거부한 사람은 서울에 살든 부산에
살든 영영 종로 날씨를 봤다.

## AI 실연동 — Gemini (2026-09-09)

`AI_PROVIDER=gemini` 로 전환했다. 날씨에 이어 **두 번째로 mock 을 벗은 서비스**다.
Gemini 를 고른 이유는 무료 등급이 있어서다. Claude 경로도 코드에 그대로 남겨뒀다.

### 프로바이더가 셋이 됐다

    mock     카탈로그 39개에서 점수로 고른다 (키 없이 동작)
    gemini   Google Gemini
    claude   Anthropic Claude

**프롬프트와 응답 스키마는 셋이 똑같은 것을 쓴다.** 바꿔 끼웠을 때 추천의
성격까지 달라지면 어느 쪽이 나은지 비교할 수 없다. 다른 건 "그 회사 API 를
어떻게 부르느냐" 뿐이다.

    Claude  도구를 하나 주고 그것으로만 답하게 한다 (tool_choice)
    Gemini  응답 스키마를 직접 넘긴다 (response_schema + response_mime_type)

목적은 같다. 문장이 아니라 정해진 JSON 으로 받는 것.

### 붙이면서 잡은 것

**1. 무료 등급은 모델이 자주 붐빈다 (503)**

`This model is currently experiencing high demand` 가 심심찮게 나온다.
3.4초에 잘 되던 요청이 몇 분 뒤 계속 실패하기도 했다.

두 단계로 막았다.
- 같은 모델로 잠깐(1.5초) 쉬었다 2번 더 시도
- 그래도 안 되면 **예비 모델로 넘어간다**

`GEMINI_MODEL` 에 쉼표로 여러 개를 적는다. `PRICE_PROVIDERS` 와 표기는 같지만
뜻이 다르다 — 가격은 적은 곳을 **전부** 조회하고, 모델은 **하나만** 쓴다.

    GEMINI_MODEL=gemini-3.7-flash,gemini-3.5-flash

429(할당량)도 같이 재시도한다. 분당 제한이면 곧 풀린다.
잘못된 키·없는 모델은 기다려도 안 풀리므로 바로 올린다.

**2. 오류 문구가 영어로 새어나갔다**

원문을 그대로 내보내면 사용자가 못 읽는다. 코드별로 한글 문구를 붙였고,
404 에는 **어느 모델이 문제인지** 이름을 넣었다. 예비 모델까지 있으면
이름이 없을 때 원인을 못 찾는다.

**3. 테스트가 진짜 API 를 부르기 시작했다**

`.env` 를 gemini 로 바꾸자 `ai_api.recommend_foods()` 를 부르던 테스트가
전부 실제 호출로 바뀌었다. 할당량이 나가고, 남의 서버가 붐비면 우리 코드는
멀쩡한데 테스트가 빨개지고, AI 는 같은 입력에 다른 답을 주니

진짜 AI 응답이 스키마에 맞는지는 테스트가 아니라 실제로 한 번 불러서 볼 일이다.

## 설계 결정 — 테이블을 안 늘리기 위해 한 것들

"테이블은 7개로 고정한다"를 지키려면 갈 곳이 없는 데이터가 네 종류 있었다.
각각을 어디에 뒀는지와 그 대가를 적는다.

### 1. AI 추천 기록 → 브라우저 (localStorage)

`/ai-history` 화면은 "언제 어떤 조건으로 뭘 추천받았는지"를 보여준다.
추천 후보를 DB에 저장하지 않는다는 원칙(§13)과 정면으로 부딪힌다.

**메뉴 이름과 조건 문장만** localStorage 에 남기기로 했다(`AiLogContext`).
레시피 본문은 저장하지 않고, 다시 열면 AI가 새로 만든다.

- 대가: 브라우저를 바꾸면 기록이 안 따라온다.
- 여러 기기에서 보이게 하려면 테이블이 하나 필요하다. 그건 설계를 바꾸는
  결정이라 지금 하지 않았다.

### 2. 찜한 레시피 → 브라우저 (기존 유지)

이름만 저장한다. 그래서 `/liked` 는 카드가 아니라 이름 목록이다.
조리시간·가격을 같이 보여주려면 찜한 개수만큼 AI 호출이 필요한데,
목록을 여는 데 그만한 시간을 쓸 이유가 없다.

### 3. 알림 → 조회할 때 만들어 낸다

`GET /api/users/me/notifications` 는 알림 테이블을 읽지 않는다.
**내 글에 달린 댓글**과 **내 글이 받은 좋아요**를 JOIN 해서 그 자리에서 만든다.

- 별도 테이블을 두면 "댓글을 지웠는데 알림만 남는" 문제를 또 관리해야 한다.
- 읽음 여부는 서버가 모른다. "마지막으로 종을 연 시각"만 브라우저에 저장하고
  (`ProfileContext`) 그보다 나중에 생긴 것을 안 읽음으로 센다.
- 내가 내 글에 단 댓글과 내가 누른 좋아요는 뺀다.

### 4. 요리 레벨 → 컬럼이 아니라 계산

`level` · `exp` 컬럼을 만들면 "글 쓸 때 +30" 같은 갱신을 기능마다 흩어놔야
하고, 한 곳만 빠뜨려도 값이 조용히 어긋난다.
확정한 식사 · 글 · 댓글 · 받은 좋아요는 이미 테이블에 다 있으므로 조회할 때 센다.

```
EXP = 요리 50 + 글 30 + 댓글 10 + 받은 좋아요 5
레벨업 필요량 = 100, 150, 200, ... (레벨마다 +50)
칭호 = 입문(1) · 초보(5) · 중수(10) · 고수(20) · 장인(30)
```

규칙을 바꾸면 과거 데이터가 자동으로 따라온다. 대신 `/api/users/me` 는
COUNT 쿼리가 네 번 돈다. 그래서 새로고침마다 부르는 `/api/auth/me` 와
**분리해 뒀다** — 그쪽은 토큰 확인용이라 가벼워야 한다.

`recommend_count`(사이드바 "추천 완료")만 서버가 모른다.
추천을 저장하지 않기 때문이다. 그건 브라우저의 AI 추천 기록 개수를 쓴다.

### 5. 카테고리 · 게임 · 공지 → 서버 파일

사용자가 만드는 값이 아니라 테이블을 만들 이유가 없고, 프론트에 두면
백엔드(AI 프롬프트)와 프론트(화면)가 서로 다른 목록을 들고 있게 된다.
실제로 냉장고 재료 칩의 글자가 서버가 아는 재료 이름과 어긋나면
아무것도 매칭되지 않는데 화면만 봐서는 이유를 알 수 없다.

`backend/app/data/catalog.json` 한 곳에서 관리하고 `GET /api/catalog` 로 내려준다.

## AI 연동 (STEP 10~11)

### Structured Output

`tools` 에 함수 하나를 알려주고 `tool_choice` 로 "반드시 이걸 써서 답해라"고
시킨다. 그러면 답이 문장이 아니라 스키마 모양의 JSON 으로 온다.
자유 텍스트로 받으면 줄바꿈 하나만 달라져도 파싱이 깨진다.

### 알레르기는 프롬프트만으로 막지 않는다

프롬프트에 "땅콩은 절대 넣지 마세요"라고 적어도 AI가 지키지 않을 수 있다.
못 지켰을 때의 결과가 심각한 조건이라, **받은 답을 서버가 한 번 더 검사해서
걸러낸다**(`ai_service.ask_ai`). 프롬프트는 부탁이고, 이 검사가 실제 방어선이다.

`DISLIKE` 는 다르게 다룬다. 빼지 않고 순위만 뒤로 미루고,
레시피에서는 `substitutes` 에 대체안을 함께 적는다.

### 예산은 생성 단계에서 제한한다

만들어놓고 걸러내면 후보가 0건이 되기 쉽다. 프롬프트에 상한을 넣고,
그래도 0건이면 예산을 3,000원 넓혀 **한 번만** 다시 물어본다.
"8천원 이하로는 없습니다" 대신 가장 가까운 대안을 준다.

### mock 프로바이더

`AI_PROVIDER=mock` 이 기본값이다. 카탈로그의 음식 39종에서 조건에 맞는 것을
골라 점수를 매긴다. **랜덤을 쓰지 않는다** — 같은 조건이면 늘 같은 결과가
나와야 화면 버그를 잡을 수 있다. 분량·가격은 재료명의 md5 에서 만든다
(파이썬 내장 `hash()` 는 서버를 다시 켤 때마다 값이 바뀐다).

검색어가 있으면 날씨 점수를 아예 안 본다. "매운 국물요리"를 찾았는데
더운 날이라고 냉면이 위로 오면 검색이 고장 난 것처럼 보이기 때문이다.

## 가격 비교 (STEP 17~19)

응답 모양은 프론트 `PriceTable` 이 기대하는 그대로다.

```json
[{ "name": "돼지고기 200g",

  전체가 죽으면 안 된다.

## 인기 레시피 기간 집계

`review_likes.created_at` 이 기준이고, **그 기간에 새로 눌린 좋아요만** 센다.
누적으로 세면 오래된 글이 영원히 1위라 순위가 움직이지 않는다.

화면에서 고른 날짜는 한국 날짜이고 DB 는 UTC 다. 그대로 비교하면 경계에서
9시간이 어긋나 새벽 0~9시 좋아요가 전날로 밀린다.
`core/kst.py` 가 변환을 맡고, 끝 날짜는 `< 다음날 0시` 로 잡는다
(`<= 23:59:59` 로 하면 그날 마지막 1초가 빠진다).

`use_yn='Y'` 조건이 세 군데 필요하다 — 글 · 좋아요 · (JOIN한) 기록.
하나라도 빠지면 취소한 좋아요나 지운 글이 순위에 섞인다.

## 논리 삭제에서 서비스 계층이 책임진 것

FK 의 `ON DELETE CASCADE` 와 참조 차단은 진짜 `DELETE` 에만 작동한다.
`UPDATE use_yn='N'` 은 DB 입장에서 그냥 값 수정이라 아무 반응도 없다
(`db/01_schema.sql` 상단 [4]). 그래서 아래 둘을 코드가 막는다.

- **회원 탈퇴** — 그 사람의 글 · 댓글 · 좋아요 · 기록 · Ban 도 함께 `'N'`
  (`user_service.withdraw`). 안 하면 탈퇴한 사람의 글이 게시판에 계속 남는다.
- **살아있는 후기가 달린 기록 삭제 차단** — 409 로 막는다
  (`history_service.delete_history`). 기록이 사라지면 게시글의 레시피가
  통째로 비기 때문이다(게시글은 복사본을 안 두고 JOIN 해서 읽는다).

탈퇴 후 토큰은 따로 무효화하지 않는다. JWT 는 발급 목록을 서버가 들고 있지
않아 취소할 방법이 없다. 대신 `core/deps.py` 가 요청마다 `use_yn` 을
확인하므로 남은 토큰으로는 아무것도 못 한다.

### 1. 좋아요 받은 레시피 — 기간 검색 (대시보드)

WHERE pl.created_at >= :start AND pl.created_at < :end + 1
```

**서버에서 할 일**

  생성 후 걸러내면 후보가 0건이 되는 경우가 잦다
- 예산을 못 맞추면 "가장 가까운 금액" 대안을 함께 내려줄 것

### 3. 최저가 / 최고가 비교

- 재료 하나당 **시장별 소매 조사가격**을 모은다 (KAMIS 는 시장·등급별로 여러 행)

- 프론트: `components/price/PriceTable.jsx` (`getPriceSummary()`로 합계 계산)

**응답 형태** — 프론트가 이 모양을 기대한다
```json
[
  { "name": "돼지고기 앞다리살 200g",
    "offers": [
      { "shop": "서울 가락시장", "price": 3980, "unit": "1kg",
        "link": "...", "surveyed_at": "20260908" },
      { "shop": "부산 엄궁시장", "price": 4350, "unit": "1kg",
        "link": "...", "surveyed_at": "20260908" }
    ] }
]
```
- `.env`의 `PRICE_PROVIDERS`를 앞에서부터 시도하고, 값이 나오면 멈춘다
  (합치면 단위 기준이 다른 값이 한 표에 섞인다)
- 값을 지어내던 mock 프로바이더는 제거했다. KAMIS 는 농수산물만 조사하므로
  두부·간장 같은 가공식품은 **가격 정보 없음**으로 두고, 합계에 몇 개를
  더한 값인지 함께 적는다
- 쇼핑몰 최저가가 아니라 **시장 조사가격**이다. 구매 링크가 없고, 단위와
  조사일자를 같이 적어야 한다. 화면에 주의 문구를 넣어뒀다
- 조사일자가 필수 파라미터인데 주말·공휴일은 조사가 없다. 일주일치를 받아와
  **가장 최근 조사일자만** 남긴다 (`latest_rows()`). 안 그러면 최저/최고가
  시장 차이가 아니라 날짜 차이가 된다
- 구분코드는 소매(01)만 쓴다. 중도매(02)와 섞으면 단가 기준이 달라 뒤죽박죽된다

### 요즘 싼 재료 추천 (services/bargain_service.py)

- KAMIS 품목 101개의 가격 흐름을 훑어 값이 내린 재료를 고르고,
  그 목록을 제미나이에게 넘겨 "싼 재료로 만드는 메뉴" 를 받는다
- 대시보드에 날씨 추천과 나란히 놓인다. 날씨가 "오늘 어떤 날인가" 로
  고른다면 이쪽은 "요즘 뭐가 싼가" 로 고른다. 축이 다르다
- **쇼핑몰 API 로는 못 만드는 기능이다.** 네이버·11번가·쿠팡은 "지금 얼마"
  만 준다. 일별 조사값이 있어야 "요즘 싼지" 를 말할 수 있다

**초당 요청 제한에 걸렸던 일** — 훑기를 동시에 두 번 돌렸다가 101개가
거의 전부 막혔다(HTTP 429). 서버 시작 시 미리 훑는 작업과 사용자 요청이
겹친 것이다. 세 가지로 막았다.

    잠금       훑기는 한 번에 하나만 돈다 (scan_lock)
    속도 조절  동시 2개 + 요청 사이 0.15초. 56초 걸리지만 안 막힌다
    파일 저장  같은 날 훑어둔 게 있으면 읽고 넘어간다 (0.02초)

파일(`app/data/bargains.json`)은 커밋해도 된다. KAMIS 는 공공데이터라
저장·공유 제한이 없고, 팀원이 인증키 없이도 실제 시세를 볼 수 있다.
(11번가는 약관 제6조 ④ 로 데이터 저장이 금지라 이렇게 못 한다.)

### 가격 추이 (integrations/price_api.py)

- "양파 지난주보다 9% 쌈" 을 재료명 옆 배지로 보여준다
- **추가 호출이 없다.** 조사일자가 필수 파라미터라 이미 일주일치를 받아놓고
  최근 하루만 쓰고 버리고 있었다. 버려지던 데이터로 만든다
- 받아온 기간의 처음 날과 마지막 날의 전국 평균을 견준다. 주말·공휴일은
  조사가 없어 날짜가 띄엄띄엄해서, "7일 전" 을 딱 집지 않는다
- 5% 미만은 알리지 않는다. 시장가는 며칠 사이에도 1~2% 씩 흔들려서,
  다 알리면 배지가 늘 떠 있어 아무 뜻이 없어진다
- **쇼핑몰 API 로는 못 만드는 값이다.** 그쪽은 지금 값만 준다.
  KAMIS 가 일별 조사값이라 가능한 일이고, 이 서비스의 차별점이다

### 레시피 캐시 (services/ai_service.py)

- 같은 음식·같은 Ban 조합이면 6시간 동안 AI 를 다시 부르지 않는다
- **31초 → 3초.** 제미나이가 붐비면 예비 모델로 넘어가느라 30초를 넘길 때가 있다.
  발표 리허설에서 같은 요리를 여러 번 여는데, 두 번째부터는 기다림이 없다
- **가격은 캐시하지 않는다.** 조회 시점의 값이라 6시간 전 값을 오늘 값으로
  보여주면 안 된다 (설계 원칙 §13). 저장할 때 `prices` 를 비운다
- 꺼낼 때 복사본을 준다. 원본을 그대로 주면 부르는 쪽이 채운 가격이
  캐시에 눌어붙어 다음 사람에게 남의 조회 결과가 나간다
- Ban 을 열쇠에 넣는다. 이름만으로 묶으면 돼지고기 알레르기가 있는 사람에게
  돼지고기가 든 레시피를 보여주게 된다
- 네이버 쇼핑 검색 API(2026-07-31 종료)를 KAMIS 로 교체했다. 쿠팡·11번가는
  제휴 승인이 필요해 보류
- 세 곳을 순차 호출하면 느리다. `httpx.AsyncClient`로 **병렬 호출**할 것

## 화면 개편 (2026-08-24) — 대시보드 시안 반영

> **`mocks/` 폴더는 2026-09-09에 삭제했다.** 아래에 "서버가 채워야 할 부분"으로
> 적어둔 것들은 전부 API로 옮겼다. 찜 목록과 AI 추천 기록만 의도적으로
> 브라우저에 남겼다(위쪽 「설계 결정」 참고).

시안(`현재UI.png`)에 맞춰 프론트를 다시 짰다. 여기 적는 건 서버가 채워야 할 부분이다.

### 새로 생긴 화면

| 경로 | 화면 | 서버가 할 일 |
|---|---|---|
| `/game`, `/game/worldcup`, `/game/balance` | 메뉴 게임 3종 | 후보 목록만 내려주면 된다. 진행은 화면에서 한다 |
| `/search?q=` | 레시피 검색 | 검색어를 **그대로 AI에 넘긴다**. "8천원 이하 파스타" 같은 문장 해석이 목적이라 SQL LIKE로는 안 된다 |
| `/fridge` | 냉장고 재료로 찾기 | 고른 재료를 프롬프트에 넣어 만들 수 있는 메뉴만 생성. 만들어놓고 거르면 0건이 되기 쉽다 |
| `/ai-history` | AI 추천 기록 | 언제·어떤 조건으로·무엇을 받았는지. 레시피 본문은 저장하지 않는다(§13 원칙 유지) |
| `/settings` | 설정 | 없음. 테마·알림은 브라우저 localStorage에만 둔다 |
| `/liked` | 찜한 레시피 | 찜 테이블이 필요하다. 지금은 `food_name` 배열을 localStorage에 둔다 |
| `/popular` | 인기 레시피 전체 | 기존 "좋아요 받은 레시피"의 이름을 바꾼 것 |

`/liked`가 **찜한 레시피**(내가 담은 것)로 바뀌었고, 남들이 많이 누른 목록은
`/popular`로 갈라졌다. 대시보드 오른쪽 순위가 후자다.

### 서버에서 채울 값

- **요리 레벨** (`MOCK_PROFILE`) — `GET /users/me` 응답에 `level` `title` `exp`
  `exp_next` `streak_days` `recommend_count` `cook_count` 를 함께 싣는다.
  퍼센트로 계산해서 내리지 말 것. 화면마다 필요한 표현이 다르다
- **알림** (`MOCK_NOTIFICATIONS`) — 읽음 여부(`read`)가 상단바 배지 숫자가 된다
- **인기 레시피 기간 집계** — 지금은 화면에서 거른다. 기간 안에 **새로 눌린**
  좋아요만 세야 한다. 누적으로 세면 오래된 글이 영원히 1위다
- **음식별 주재료** (`MOCK_FOOD_INGREDIENTS`) — 냉장고 찾기 매칭용

### 다크 모드

`<html data-theme="dark">` 한 곳만 바뀌고 색은 전부 `styles/index.css`의
CSS 변수에서 갈린다. **컴포넌트 CSS에 색상 리터럴(`#fff` 등)을 새로 적지 말 것.**
적는 순간 그 자리만 라이트 모드로 남는다. 흰 배경 위에 얹는 하트 버튼처럼
의도적으로 고정한 곳에는 주석을 달아뒀다.

첫 페인트 전에 테마를 정하려고 `index.html`에 인라인 스크립트를 하나 뒀다.
React가 뜬 뒤에 칠하면 다크 모드 사용자에게 흰 화면이 한 프레임 번쩍인다.

|---|---|---|---|
| `routers/bans.py` | 리스트 컴프리헨션 (프로젝트 마지막 1곳) | `[BanResponse.model_validate(b) for b in bans]` | `for` 루프 + `append` |

### `?.` 와 `??` — 없애지 않고 문서로 뺐다

프론트엔드 24개 파일에 58곳 쓰인다. 정책이 문서에 없어서 이번에 정했다.

**없애지 않는다.** 없애면 `if` 문 8줄이 되어 오히려 어려워지고,
안 쓰면 서버 응답이 비었을 때 리액트 화면이 통째로 하얘진다.

대신 `STUDY_JS_SYNTAX.md` 를 새로 썼다.

> 이 문서는 2026-09-18 「소스 단계 낮추기」에서 지웠다. 지금 `docs/` 에
> 남은 STUDY_ 문서는 `STUDY_AUTH.md` · `STUDY_COLUMN_TYPES.md` 둘이다.
`?.` · `??` 두 개만 다루고, **`||` 와 `??` 의 차이**(`0` 과 빈 문자열을
기본값으로 바꾸느냐)를 표로 정리했다.

소스에는 헷갈리는 3곳에만 주석을 더 넣었다. 같은 설명을 58번 적으면
그게 더 읽기 어렵다.

- `api/client.js` — 문서 위치를 적어뒀다 (모두가 제일 먼저 여는 파일)
- `Roulette.jsx` — `?.(` 는 속성이 아니라 **함수 호출**을 건너뛰는 모양이다
- `RecommendPage.jsx` — 여기만 `??` 가 아니라 `||` 다. 이유를 안 적으면 실수로 보인다

## 남은 파일 마무리 — 스타일 통일 (2026-09-06)

앞선 작업은 "어려운 문법이 있는 파일"만 골라서 고쳤다.
그러다 보니 손댄 파일과 안 손댄 파일의 **스타일이 섞여버렸다.**
한 프로젝트 안에 두 가지 방식이 있으면 초보에게는 오히려 더 헷갈린다.

### 무엇을 통일했나

| 무엇 | 전 | 후 |
|---|---|---|
| 이벤트 핸들러 선언 | `const onSubmit = (e) => {...}` (22곳) | `function onSubmit(e) {...}` (전부) |
| `alive` 플래그 | 파일마다 있기도 없기도 | 아래 규칙으로 정리 |

손댄 파일 17개: TopBar · Sidebar · CategoryBar · DateRangeFilter · BudgetPicker ·
BudgetRange · FoodFinder · Roulette · MainLayout · MyPage · SettingsPage ·
CommunityPage · HistoryPage · RecipePage · LoginPage · RegisterPage · PostWritePage

### `alive` 플래그 — 지운 곳과 남긴 곳

똑같아 보이지만 하는 일이 다르다.

**지웠다 (HistoryPage · MyPage)**
의존성이 `[]` 라서 화면이 열릴 때 한 번만 실행된다.
플래그가 막아주는 건 "화면을 떠난 뒤 도착한 응답"뿐인데,
리액트 18부터는 그때 setState 를 불러도 아무 일도 안 일어난다. 읽을 거리만 늘린다.

**남겼다 (CommunityPage)**
의존성이 `[keyword]` 라서 **검색어를 고칠 때마다 다시 실행된다.**
요청은 보낸 순서대로 도착하지 않는다. "김" 의 응답이 "김치" 의 응답보다 늦게 오면
화면에 "김치" 결과가 떴다가 "김" 결과로 덮인다.
이건 실제로 나는 버그라 플래그가 꼭 필요하다. 대신 왜 필요한지 주석에 풀어 적었다.

> 같은 코드라도 의존성 배열이 `[]` 인지 `[무언가]` 인지에 따라 필요/불필요가 갈린다.

| `mocks/index.js` (1,421줄) | 순수 데이터 |
| `styles/**/*.css` | 이번 작업 범위가 아니다 |

### 검증하다 잡은 것

**1. `price_api.py` — 조용히 넘어가는 회귀**

실패하면 그걸로 되돌리게 고쳤다. 결과적으로 원본보다 읽기도 쉽다.

## 프론트엔드 코드 난이도 낮추기 (2026-09-06)

백엔드에 이어 리액트 쪽도 같은 기준으로 정리했다.
**화면 동작과 API 호출은 그대로다.** 문법과 구조만 손봤다.

### 무엇을 바꿨나

| 무엇 | 전 | 후 |
|---|---|---|
| `api/client.js` | 모듈 전역 `authToken` + `setAuthToken()` 으로 동기화 | 요청할 때 `getToken()` 으로 localStorage 에서 바로 읽음 |

### 남긴 것과 이유

- **`onTokenExpired` 콜백 하나** — `client.js` 가 `AuthContext` 를 직접 import 하면
  순환 참조가 된다. 왜 이 방향인지 주석에 적어뒀다.
- **`PostDetailPage` 의 낙관적 갱신** — 하트가 즉시 반응해야 눌린 느낌이 난다.

### 작업 중 잡은 버그

`PostDetailPage` 좋아요를 함수형 업데이트(`setLikeCount(n => n + 1)`)에서
직접 값 계산으로 바꾸다가, **실패 시 되돌리는 값이 1 어긋나는** 문제를 만들었다가 잡았다.
누른 순간의 값을 `previousLiked` / `previousCount` 에 먼저 담아두고
실패하면 그 값으로 되돌리는 방식으로 고쳤다 — 결과적으로 원본보다 읽기도 쉽다.

## 스키마 v2 (2026-09-04) — 논리 삭제 · 후기 게시판 FK

### 무엇이 바뀌었나

| # | 변경 | 이유 |
|:--:|---|---|
| 1 | 6개 테이블에 `USE_YN CHAR(1)` 추가 | 삭제 · 탈퇴를 물리 삭제 대신 `'N'` 갱신으로 |
| 2 | `UNIQUE` 제약 4개 → 함수 기반 UNIQUE 인덱스 | `'N'` 행이 자리를 차지해 재등록이 막히는 것을 방지 |
| 3 | `POSTS` → `RECIPE_REVIEWS` | "레시피 추천" 게시판이라는 성격을 이름에 반영 |
| 4 | `RECIPE_REVIEWS`에 `MEAL_HISTORY_ID` 합성 FK 추가 | 직접 만들어본 요리만 후기를 쓸 수 있게 DB가 강제 |
| 5 | `POST_LIKES` → `REVIEW_LIKES`, `COMMENTS` → `REVIEW_COMMENTS` | `post_id` → `review_id` |
| 6 | `USERS`에 `GENDER` + 주소 4개 컬럼 추가 | 대시보드 첫 화면의 날씨 조회 (STEP 12) |

`VERIFICATION_CODES`에는 `USE_YN`을 붙이지 않았다. OTP는 사용자가 삭제하는
데이터가 아니고 `used_at` / `expires_at`으로 이미 생명주기를 관리한다.

### 왜 UNIQUE를 인덱스로 바꿨나

논리 삭제에서 가장 먼저 터지는 곳이다. `uq_post_likes(user_id, post_id)`가
평범한 UNIQUE면, 좋아요를 취소(`'N'`)한 뒤 다시 누르는 순간 `ORA-00001`이 난다.
행이 그대로 남아 있기 때문이다. 같은 문제가 Ban 재등록 · 탈퇴 이메일 재가입에도 있다.

```sql
CREATE UNIQUE INDEX uq_review_likes ON review_likes (
    CASE WHEN use_yn = 'Y' THEN user_id   END,
    CASE WHEN use_yn = 'Y' THEN review_id END
);
```

`'N'` 행은 모든 키 컬럼이 `NULL`이 되어 인덱스에 들어가지 않는다.
살아있는 행끼리만 유일성을 본다.

**대신 이 인덱스는 `WHERE user_id = :v` 조회에 쓰이지 않는다.** 선두가 표현식이라
옵티마이저가 매칭하지 못한다. 그래서 조회용 일반 인덱스를 `(col, use_yn)`으로
따로 만들었다. `idx_users_email` · `idx_user_bans_user` · `idx_review_likes_review`가 그것이다.

### 왜 합성 FK인가

```sql
CONSTRAINT fk_reviews_meal FOREIGN KEY (meal_history_id, user_id)
                           REFERENCES meal_histories (id, user_id)
```

`meal_history_id` 하나만 참조하면 "존재하는 히스토리"인 것만 보장되고,
**남의 히스토리를 자기 후기로 공유하는 것**은 막지 못한다. 쌍으로 걸면
글쓴이와 히스토리 주인이 다를 때 DB가 `ORA-02291`로 거부한다.
Oracle은 PK/UNIQUE 조합만 참조 대상으로 허용하므로
`meal_histories`에 `uq_meal_id_user UNIQUE (id, user_id)`를 함께 넣었다.

### FK로 못 막는 것 — 서비스 계층의 책임

`ON DELETE CASCADE`와 참조 차단은 **진짜 `DELETE`에만 작동한다.**
`UPDATE use_yn='N'`은 DB 입장에서 그냥 값 수정이라 아무 반응도 없다. 그래서:

- **회원 탈퇴** — `users`만 `'N'`으로 바꾸면 그 사람의 후기 · 댓글 · 좋아요는
  `'Y'`로 남아 화면에 계속 보인다. 하위 테이블까지 연쇄 UPDATE 해야 한다.
  → `user_service.withdraw()` 가 `ReviewLike` · `ReviewComment` ·
  `RecipeReview` · `MealHistory` · `UserBan` 다섯 표를 훑는다. **✅**
- **"후기가 있으면 히스토리 삭제 금지"** — 논리 삭제는 FK가 못 막는다.
  `'N'`으로 바꾸기 전에 살아있는 후기가 있는지 검사해야 한다.
  → `history_service.delete_history()` 가 확인하고 409 를 낸다. **✅**

`NOTICES` 는 탈퇴 연쇄에서 일부러 뺐다
--------------------------------------
공지도 `user_id` 와 `use_yn` 을 가지고 있어서 위 목록에 넣을 수 있게 생겼는데,
넣으면 안 된다. 공지는 개인의 글이 아니라 운영팀이 서비스 이름으로 낸 글이라,
쓴 사람이 그만뒀다고 "서버 점검 안내" 가 같이 사라지면 곤란하다.

DDL 도 같은 판단이다 — 하위 표 중 `fk_notices_user` 에만 `ON DELETE CASCADE`
가 없다. 여기에 `Notice` 를 더하면 그 설계를 코드가 조용히 뒤집는다.

### 실측으로 확인한 것 (25건 중 24건 통과, 1건은 테스트 쪽 오류)

| 확인한 동작 | 결과 |
|---|---|
| 남의 히스토리로 후기 작성 | `ORA-02291` 거부 ✅ |
| 같은 식사로 후기 2번 | `ORA-00001` 거부 ✅ |
| 후기 삭제(`'N'`) 후 같은 식사로 재작성 | 성공 ✅ |
| 좋아요 취소 후 재클릭 | 성공 ✅ |
| Ban 해제 후 같은 재료 재등록 | 성공 ✅ |
| 탈퇴 후 같은 이메일 재가입 | 성공 ✅ |
| 재가입 계정이 살아있는 동안 탈퇴 계정 복구 | `ORA-00001` 거부 (정상) ✅ |
| 후기가 달린 히스토리 `DELETE` | `ORA-02292` 거부 ✅ |
| 후기가 달린 **회원** `DELETE` | **통과됨.** 연쇄 삭제가 `recipe_reviews`를 먼저 지워서 막히지 않는다. `DELETE FROM users`를 손으로 실행하면 그 회원의 모든 데이터가 사라진다 ⚠️ |

## 설계 결정 기록

### 왜 CSS를 styles/ 아래로 몰았나 (2026-08-23)
JSX와 CSS가 한 폴더에 섞여 있어 `pages/`를 열면 파일 수가 두 배로 보였다.
`src/styles/` 아래에 **소스 폴더 구조를 그대로 미러링**해서 옮겼다.

```
src/pages/LoginPage.jsx           -> import '../styles/pages/LoginPage.css'
src/components/common/TopBar.jsx  -> import '../../styles/components/common/TopBar.css'
```

`src/styles/index.css`는 전역이라 그대로 뒀다.
CSS 파일을 새로 만들 때도 이 규칙을 따를 것. 클래스명 규칙(BEM 풍의
`.mypage__ban-name`)은 바뀐 게 없다.

### 왜 Ban 추가는 사전 조회 없이 IntegrityError만 잡나
회원가입(`register_user`)은 이메일/닉네임 **두 개**의 UNIQUE가 있어서, 어느 쪽이
중복인지 알려주려고 사전 `SELECT`를 한 번 한다. Ban은 `uq_user_bans` 하나뿐이라
`IntegrityError`가 곧 "재료명 중복"이다. 사전 조회를 넣어봐야
SELECT-INSERT 사이의 경합은 못 막으면서 쿼리만 늘어난다.

### 왜 남의 Ban을 지우려 하면 403이 아니라 404인가
403은 "권한은 없지만 그 리소스는 존재한다"는 뜻이 된다. id를 1씩 올려가며
403/404를 세면 남의 Ban이 몇 개인지 알 수 있다. 없는 id와 남의 id를 같은 404로
묶어서 그 차이를 없앴다.

### 왜 재료명을 스키마에서 `strip()` 하나
`'오이'`와 `'오이 '`는 다른 문자열이라 `uq_user_bans`가 중복으로 보지 않는다.
DB에 닿기 전에 잘라내야 UNIQUE 제약이 의도대로 동작한다. 회원가입 닉네임과 같은 이유다.

### 왜 PostgreSQL에서 Oracle로 바꿨나
프로젝트 방침 변경. 전환 시점에 SQLAlchemy 모델을 하나도 안 만든 상태여서
비용이 거의 없었다. 영향 파일은 5개뿐이었고 프론트엔드는 수정 0건.

### 왜 change 단계에서 코드 행을 지우나
`used_at`이 찍힌 코드는 `verify`를 다시 통과하지 못하지만, `change`는
"`used_at`이 있는가"를 조건으로 삼기 때문에 같은 코드로 몇 번이든 호출할 수 있다.
비밀번호를 바꾼 뒤 행을 삭제해서 그 구멍을 막는다.

### 왜 `verification_codes.used_at` 컬럼을 뒀나
`verify-code`와 `change`가 별도 엔드포인트라, 인증 성공 사실을 어딘가 남겨야
`change` 단계에서 "검증된 요청"인지 판별할 수 있다. 없으면 같은 코드로
비밀번호를 여러 번 바꿀 수 있다(OTP 일회성 위반).

### 왜 JSON을 CLOB에 넣나
Oracle 21c에 네이티브 `JSON` 타입이 있지만 **SQLAlchemy 2.0.52의 Oracle
dialect가 지원하지 않는다** (`visit_JSON` 미구현 → `CompileError`).
`CLOB` + `CHECK (... IS JSON)`이 유일하게 성립하는 선택지.
레시피 JSON은 통째로 읽고 쓰는 스냅샷이라 성능 손실도 무의미하다.

### 왜 passlib 대신 bcrypt를 직접 쓰나
passlib 1.7.4는 2020년 이후 릴리스가 없어 bcrypt 5.x와 호환되지 않는다.
`AttributeError: module 'bcrypt' has no attribute '__about__'`.

### 왜 로그인 실패 시 남은 횟수를 알려주나
사용성을 위해 그렇게 정했다 (2026-08-17).

단, 이건 트레이드오프다. `(남은 시도 N회)` 문구는 **존재하는 계정에만** 붙으므로,
없는 이메일과 응답을 비교하면 가입 여부를 알아낼 수 있다.
"없는 이메일과 틀린 비밀번호를 구분하지 않는다"는 로그인 정책이 이 부분에서는
사실상 무력해진다.

계정 열거를 막는 쪽으로 바꾸려면 `login_user()`의 401 메시지를
`_INVALID_CREDENTIALS` 상수로 되돌리면 된다. 그 한 줄이 전부다.

> 가입되지 않은 이메일에 404 를 준다. 로그인에서 이미 열려 있는 것을
> 여기서만 가려봐야 실효가 없고, 오타를 쳐도 "보냈습니다" 가 뜨는 쪽이
> 사용자에게 더 나쁘다. 아래 「가입되지 않은 이메일에 알려주기」 참고.

### 로그인 응답 시간은 맞추지 않는다 (2026-09-12 결정)

`login_user()` 는 없는 이메일이면 `verify_password()` 까지 가지 않고 곧바로
401 을 던진다. bcrypt 해시 비교가 일부러 무겁게 설계돼 있어서, 그 단계를
건너뛰는 것과 거치는 것의 응답 시간이 크게 갈린다. 실측하면 이렇다.

    가입 안 된 이메일   HTTP 401   중앙값 6.6ms
    가입된 이메일       HTTP 401   중앙값 321.1ms      <- 약 50배

응답 내용은 둘 다 같은 401 인데 **시간만 재면 가입 여부를 알 수 있다.**
막으려면 없는 이메일일 때도 버릴 해시 계산을 한 번 돌려 시간을 맞추면 된다.

    if user is None:
        verify_password(payload.password, DUMMY_HASH)   # 결과는 안 쓴다
        raise HTTPException(401, INVALID_CREDENTIALS)

**넣지 않기로 했다.** 세 줄이면 되지만 혼자 넣으면 아무 효과가 없다.
같은 정보가 더 쉬운 경로로 이미 열려 있기 때문이다.

    로그인 시간 재기    요청 여러 번 + 통계 + 네트워크 지연 감안
    로그인 문구 보기    한 번. (남은 시도 N회) 가 붙는지만 보면 된다
    재설정에 넣어보기   한 번. "가입되지 않은 회원입니다" 라고 대놓고 알려준다

세 번째가 STEP 32 에서 **일부러 그렇게 만든** 동작이다. 앞문을 열어두고
뒷문에 자물쇠를 다는 셈이라, 코드만 늘고 얻는 것이 없다.

계정 열거를 정말 막기로 한다면 **세 곳을 같이** 닫아야 한다.

    1) login_user() 의 401 문구를 INVALID_CREDENTIALS 로 되돌린다
    2) send_reset_code() 의 404 를 return 으로 되돌린다 (STEP 32 취소)
    3) 위의 DUMMY_HASH 를 넣는다

하나만 닫으면 닫힌 것처럼 보이기만 한다. 그래서 이건 "아직 못 한 일" 이
아니라 **정책을 맞춘 결과**다 — 「남은 것」 표에서 뺀 이유다.

### 왜 좋아요/댓글 수를 컬럼으로 안 두나
MVP에서는 `COUNT()` 집계로 충분하다. 비정규화 컬럼은 동기화 버그 위험이
성능 이득보다 크다.

## ⚠️ Oracle 관련 함정 (실측으로 확인한 것들)

앞으로 코드 쓸 때 계속 걸리는 것들이라 기록해둔다.

### 1. `VARCHAR2(n)`은 바이트 단위다
```sql
VARCHAR2(50)        -- 한글 16자에서 잘림 (DB가 BYTE 시맨틱)
VARCHAR2(50 CHAR)   -- 한글 50자 정상        <- 반드시 이렇게
```
이 DB의 `NLS_LENGTH_SEMANTICS`는 `BYTE`다. SQLAlchemy는 자동으로 `CHAR`를
붙여주지만, 수기 DDL에서는 직접 써야 한다.

### 2. 타임존이 조용히 어긋난다 (가장 위험)
python-oracledb는 tzinfo를 **저장·조회 양방향에서 버린다.**
```
바인딩: 08:00+00:00 (UTC)  ->  DB 저장: 08:00 +09:00   ← 9시간 오차, 에러 없음
조회  : DB의 +09:00 값      ->  파이썬: tzinfo=None
```
**대응**: DB에는 UTC만 저장한다.
- DDL: `TIMESTAMP(6) DEFAULT SYS_EXTRACT_UTC(SYSTIMESTAMP)`
- 모델: `models/types.py`의 `UtcTimestamp` 타입 사용 (경계에서 변환)
- 커넥션: 접속 시 `ALTER SESSION SET TIME_ZONE='+00:00'` (database.py)

### 3. 빈 문자열이 NULL이다
`''`를 `NOT NULL` 컬럼에 넣으면 `ORA-01400`으로 500이 난다.
Pydantic 스키마에 `min_length=1`을 반드시 건다.

### 4. `SELECT 1`이 안 된다
Oracle은 FROM 절이 필수다. `SELECT 1 FROM DUAL`.

### 5. DBeaver가 빈 줄에서 SQL을 자른다
`CREATE TABLE` 안에 빈 줄이 있으면 문장이 쪼개져 `ORA-00900`이 난다.
DDL 파일은 이미 빈 줄을 제거해뒀다.
설정으로도 끌 수 있다: Preferences → Editors → SQL Editor → SQL Processing
→ "Blank line is statement delimiter" → Never

### 6. `ON CONFLICT` / `ILIKE`가 없다
- 중복 INSERT: `MERGE` 또는 `IntegrityError` 캐치 (STEP 22 좋아요에서 필요)
- 대소문자 무시 검색: `LOWER(col) LIKE LOWER(:kw)` (STEP 20 게시판 검색)

### 7. `DROP TABLE IF EXISTS`가 없다
21c에는 없다(23ai부터). `db/00_drop_all.sql`처럼 PL/SQL로 우회.

### 8. bcrypt는 72바이트가 상한이다
한글 비밀번호는 24자가 최대. `schemas/auth.py`에서 바이트 기준으로 검증한다.

### 9. 리스너가 설치 시점의 IP에 고정된다 (개인 PC 설치 시)
XE를 설치하면 `listener.ora`에 그 순간의 IP가 박힌다.
```
(ADDRESS = (PROTOCOL = TCP)(HOST = 192.168.219.101)(PORT = 1521))
```
이러면 `localhost` 접속이 거부된다 — `DPY-6005` / `WinError 10061`.
서비스는 Running이고 DBeaver가 IP로 붙으면 되기 때문에 원인을 찾기 어렵다.

**대응**: `<ORACLE_HOME>/network/admin/listener.ora`에서 `HOST`를 `0.0.0.0`으로
바꾸고 `OracleOraDB21Home1TNSListener` 서비스를 재시작한다.
IP를 직접 적으면 다른 네트워크(집↔학원)로 이동할 때마다 다시 깨진다.

확인: `Get-NetTCPConnection -State Listen -LocalPort 1521` 이 `0.0.0.0`을 보여야 한다.

## ⚠️ Windows 개발환경 함정

### 1. pip가 requirements.txt를 cp949로 읽는다
한글 Windows에서 pip는 BOM이 없으면 **OS 기본 인코딩(cp949)** 으로
requirements.txt를 읽는다. 파일에 한글 주석이 있으면 설치가 통째로 실패한다.
```
UnicodeDecodeError: 'cp949' codec can't decode byte 0x80 in position 10
```
**대응**: `requirements.txt`를 **UTF-8 with BOM**으로 저장한다. pip는 BOM을
먼저 검사하므로 pip 버전·OS 로케일과 무관하게 동작한다. (2026-08-17 적용 완료)

### 2. 기본 python이 3.11 미만일 수 있다
이 프로젝트는 Python 3.11+ 가 필요하다. `python --version`이 3.9 등이면
venv 생성 시 버전을 명시한다.
```
py -3.11 -m venv .venv
```

## 팀 공용 DB 주의사항

`10.1.54.120:1521/XEPDB1`을 팀원 전체가 공유한다.

- 한 명이 DDL을 실행하면 **전원에게 반영**된다. `00_drop_all.sql` 실행 전 공지할 것

  `test-{본인이름}@example.com` 식으로 구분해서 쓸 것
- XE는 동시 세션 수에 제약이 있어 `DB_POOL_SIZE=5`로 작게 잡아뒀다

`10.1.54.120`은 **사내망 주소**라 집에서는 접속이 안 된다. 선택지:

| 방법 | 비고 |
|---|---|
| VPN | 사내망에 붙을 수 있으면 그대로 사용 |

`DB_HOST` 한 줄만 바꾸면 되도록 설계해뒀다.
