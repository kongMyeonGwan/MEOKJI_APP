## 비 오는 날 추천 (2026-09-11)

날씨를 받아오기만 하고 점수에 안 쓰던 것을 연결했다. **28도 장마날에 냉면이
1등으로 올라오던 것**이 이 작업의 출발점이다.

### 어디가 비어 있었나

`condition` 은 이미 다 흐르고 있었다.

    weather_api      CLEAR / CLOUDS / RAIN / SNOW 를 만들어 내려준다   ✅
    AI 프롬프트      "오늘 날씨: ... 비 25도" 로 넣고 있었다            ✅
    화면             비 배경 · 🌧️ 이모지를 이미 그리고 있었다           ✅
    score_weather()  temp 만 읽고 condition 을 안 봤다                  ❌

빠진 곳은 **점수 계산 한 군데**였다. 그래서 진짜 AI(gemini)를 쓸 때는 비가
반영됐고, mock 이나 AI 가 죽어 카탈로그로 떨어질 때만 안 됐다.
"가끔 되는" 상태가 제일 찾기 어렵다.

### 기온과 하늘을 따로 재서 더한다

    score_weather = score_temperature(temp) + score_sky(condition)

둘은 서로 독립이다 — 장마철에는 28도인데 비가 오고, 12월에는 5도인데 맑다.
한쪽이 다른 쪽을 덮어쓰지 않고 더하기만 한다.

    눈 오는 추운 날의 국물   +6 +7 = +13   같은 방향이면 더 세게
    비 오는 더운 날의 냉면   +8 -5 =  +3   반대면 서로 깎는다

`score_weather()` 를 지우지 않고 남긴 이유는 부르는 쪽(`score_food`)이
날씨 딕셔너리 하나만 넘기면 되게 하기 위해서다. 안을 둘로 나눈 것뿐이다.

### 점수

    RAIN   국물 +6   튀김 +4   찬 음식 -5
    SNOW   국물 +7             찬 음식 -8
    CLEAR · CLOUDS · 모르는 코드 · None   전부 0

비에 튀김을 넣은 건 부침개 자리다. 기온만 보면 절대 안 올라온다.

눈을 더 세게 준 이유는 기온 점수와 겹치기 때문이다. 겹치는 쪽으로 확실히
밀어주는 편이 맞다 — 눈 오는 날 냉면을 추천받고 싶은 사람은 없다.

### '시원한음식' 태그만 보면 샌다

찬 음식을 뒤로 미는 데 태그 하나만 쓰면 **회냉면 · 비빔국수가 빠져나간다.**
둘 다 `여름메뉴` 만 달려 있고 `시원한음식` 이 없다.

그래서 `is_cold_dish()` 를 따로 뒀다.

    HOT_WEATHER_PICKS 에 있거나 · '시원한음식' 이거나 · '여름메뉴' 이거나

`HOT_WEATHER_PICKS` 는 원래 "더운 날 먼저 보여줄 메뉴" 목록인데, 들어있는
15건이 전부 차게 먹는 것이라 그대로 쓸 수 있었다.

**추운 날 규칙에도 같이 적용했다.** 원래 `"시원한음식" in tags` 만 보고
있어서, 영하 2도에 회냉면이 안 밀리고 있었다. 비 작업을 하다 같이 잡혔다.

### 문구도 같이 고쳐야 했다

점수만 고치면 **왼쪽 문구와 오른쪽 카드가 다른 말을 한다.** 비 오는 18도에
카드는 국물을 미는데 문구는 "선선한 날엔 든든한 한 끼" 라고 말한다.

    오늘은 비 오고 선선한 날씨에요!          <- 첫 줄은 늘 하늘 + 기온
    따끈한 국물이나 바삭한 튀김이 당기는 날이에요   <- 둘째 줄만 갈린다

`make_pick_lead()` 가 `condition` 을 받게 바꿨다. 사람도 비가 오면 기온보다
비를 먼저 말한다 — "오늘 15도네" 가 아니라 "비 오네" 다.

프론트는 손대지 않았다. `pick_lead` 를 그대로 그리고 있었고, 비 배경과
🌧️ 이모지는 이미 `condition` 으로 고르고 있었다.

### 옛 호출부가 그대로 돈다

`condition` 이 없으면 `score_sky()` 가 0 이라, `{"temp": 30}` 만 넘기던
기존 테스트와 호출부가 전과 똑같이 동작한다. 모르는 코드(`"TORNADO"`)가
와도 0 이다 — 날씨 API 가 새 코드를 내보내도 터지지 않는다.

### 검증

실제로 추천이 갈리는지 돌려봤다.

    28도 CLEAR  ->  오이냉국, 미숫가루 셰이크, 열무국수, 김치말이국수
    28도 RAIN   ->  소고기 쌀국수, 간짜장, 간단 돈까스, 크림 파스타
    18도 CLEAR  ->  전자레인지 계란찜, 오이냉국, 미숫가루 셰이크, 충무김밥
    18도 RAIN   ->  콩나물국밥, 된장찌개, 들깨 수제비, 김치찌개

테스트가 175건 -> 185건이 됐다. 새로 10건이다.

    같은 기온이어도 비가 오면 추천이 달라진다
    비 오는 날에는 찬 음식이 위로 안 온다
    비 오는 날에는 국물이나 튀김이 먼저 나온다
    눈 오는 날은 같은 기온의 맑은 날보다 찬 음식을 더 민다
    맑음과 흐림은 점수에 영향이 없다        모르는 코드 · None 포함
    condition 이 없는 날씨도 그대로 돈다    옛 호출부 보호
    여름메뉴 태그만 있어도 찬 음식으로 친다  회냉면 · 비빔국수
    비 오는 날 문구는 기온 대신 비를 말한다
    비 오는 날 머리말도 비를 말한다
    맑은 날 문구는 그대로 기온을 따른다

## 게시판 페이징 (2026-09-11)

목록을 한 번에 다 내려주던 것을 20건씩 끊었다. 글이 수백 건이 되면 CLOB 은
안 실어도 본문 미리보기 · 좋아요 · 댓글 수를 전부 세어 내려주게 된다.

### 응답을 한 겹 감쌌다

    전:  [ {...}, {...} ]
    후:  { items: [...], total: 137, page: 3, size: 20, total_pages: 7 }

화면이 "3 / 7" 을 그리려면 **전체가 몇 건인지** 알아야 한다. 20건짜리 배열만
와서는 이게 마지막 페이지인지 알 방법이 없다. 개수를 응답 헤더에 담는 방법도
있지만, 본문에 같이 두면 `/docs` 에도 보이고 프론트도 `data.total` 로 그냥
읽는다.

목록 응답 모양이 바뀌었으므로 `getPosts` 를 쓰는 쪽(`CommunityPage`)과
기존 테스트 2건도 같이 고쳤다.

### COUNT 와 목록이 같은 조건을 봐야 한다

쿼리가 두 번 나간다 — 전체 건수를 세는 COUNT 와, 이 페이지 몫을 읽는 목록.
**한쪽에만 검색어를 붙이면** "7페이지가 있다" 고 해놓고 열면 비어 있는 화면이
된다. JOIN 도 양쪽을 맞춰뒀다.

한 번에 다 읽어서 파이썬에서 잘라도 결과는 같지만, 그러면 천 건을 읽어놓고
20건만 쓰게 된다. 자르는 일은 DB 가 해야 한다.

### 정렬에 id 를 같이 넣은 이유

`created_at` 만으로 정렬하면 시각이 같은 글 둘의 순서를 DB 가 마음대로
정한다. 페이지를 넘길 때마다 순서가 달라지면 **같은 글이 1페이지와 2페이지에
다 나오거나, 어느 페이지에도 안 나온다.** id 는 겹치지 않으므로 순서가 항상
똑같이 정해진다.

원래도 `.order_by(created_at.desc(), id.desc())` 로 되어 있었다. 페이징이
없을 때는 없어도 티가 안 나던 것이 이제 필요해진 것이다.

### 좋아요 · 댓글 수를 페이지 몫만 센다

`count_likes_by_post()` 가 인자로 `post_ids` 를 받게 바꿨다. 없으면 1페이지
20건을 보여주려고 전체 글의 좋아요를 다 세게 된다. 이제 글이 수천 건이 돼도
세는 양이 20건어치로 고정된다.

(Oracle 의 `IN` 은 1000개가 상한이다. `size` 상한이 50 이라 걸릴 일이 없다.)

### size 에 상한을 뒀다

`?size=100000` 한 번으로 글 전체를 끌어올 수 있으면 페이징을 붙여놓고
우회로를 열어두는 셈이다. 50 을 넘으면 422 다.

범위를 벗어난 `page` 는 404 가 아니라 **빈 items** 다. 9999 페이지를 열었다고
에러 화면이 될 일은 아니고, 화면이 `total_pages` 를 보고 되돌리면 된다.

### 검색어를 state 두 개로 나눴다

    keyword   입력칸에 지금 찍혀 있는 글자
    query     실제로 서버에 보낸 검색어 (타이핑이 멎고 0.3초 뒤에 따라온다)

전에는 하나였고 `getPosts` 호출 자체를 `setTimeout` 으로 감싸고 있었다.
페이징이 붙으면서 **페이지 버튼을 눌러도 0.3초를 기다리게** 되어버려서,
기다리는 것(검색어)과 즉시 나가는 것(페이지)을 갈랐다. effect 도 둘로 나뉘어
각자 하는 일이 하나씩이다.

검색어가 바뀌면 `page` 를 1 로 되돌린다. 3페이지를 보다가 검색하면 결과가
2건인데 3페이지를 달라고 해서 빈 화면이 뜬다.

"검색 결과가 없습니다" 문구도 `keyword` 가 아니라 `query` 를 본다. 타이핑
도중에는 아직 이전 결과가 떠 있는데, `keyword` 로 판단하면 목록보다 문구가
먼저 바뀐다.

### 새로 생긴 것

    backend/app/schemas/post.py       PostPage
    frontend/src/components/common/Pagination.jsx
    frontend/src/styles/components/common/Pagination.css

`Pagination` 은 현재 페이지 둘레로 ±2 개만 그리고 나머지는 `…` 로 접는다.
글이 2000건이면 페이지가 100개인데 다 그리면 버튼이 화면을 덮는다. 첫 페이지와
끝 페이지는 항상 남긴다 — 100페이지에서 1페이지로 한 번에 갈 길이 필요하다.

**딱 한 칸만 비면 `…` 대신 그 번호를 그대로 쓴다.** `…` 도 한 칸을 차지해서,
접어봐야 좁아지지 않는데 클릭만 못 하게 된다.

    page=1  total=100  ->  1 2 3 … 100
    page=3  total=100  ->  1 2 3 4 5 … 100
    page=50 total=100  ->  1 … 48 49 50 51 52 … 100

### 검증

통합 테스트가 169건 -> 175건이 됐다. 새로 6건이다.

    목록은 페이지 정보와 함께 온다        total_pages 가 올림인지
    한 페이지 크기를 줄이면 그만큼만 온다
    다음 페이지는 앞 페이지와 겹치지 않는다   정렬이 고정됐는지
    범위를 벗어난 페이지는 빈 목록이다        404 가 아니다
    페이지 번호는 1부터다                     0 이면 OFFSET 이 음수가 된다
    한 페이지 크기에는 상한이 있다            51 은 422, 50 은 200

검색 테스트에는 `total` 검증을 더했다. COUNT 에서 검색 조건을 빠뜨리는 것이
이 기능에서 가장 나기 쉬운 버그인데, 결과 건수만 보면 안 잡힌다.

`Pagination.makeItems()` 는 node 로 직접 돌려 위 표를 확인했다
(프론트에는 테스트 러너가 없다).

**168 통과 / 7 실패.** 실패 7건은 이 작업과 무관하다 — 로컬 DB 에
`db/04_notices_and_games.sql` 이 아직 안 돌아서 나던 것이 그대로다.

## 공지사항과 미니게임 기록 (2026-09-10)

테이블 두 개(`NOTICES` · `GAME_HISTORIES`)가 DDL 에만 있고 백엔드가 쓰지
않던 것을 실제로 연결했다. 이로써 표 9개를 전부 쓴다.

### 공지를 파일에서 DB 로

`catalog.json` 에 다섯 건이 하드코딩돼 있었다. 카테고리 칩·룰렛 조각과
한 묶음으로 "사용자가 만들지 않는 목록" 취급을 한 것인데, **성격이 다르다.**

    카테고리 칩   개발자가 정한다. 바뀌면 코드도 같이 바뀐다
    공지사항      운영자가 계속 새로 쓴다. 코드와 무관하다

파일에 두면 공지 하나 올릴 때마다 서버를 다시 배포해야 한다. 그래서
`NOTICES` 표로 옮겼고, 주소도 `/api/catalog/notices` → `/api/notices` 로
옮겼다. 있던 다섯 건은 `db/05_seed_notices.sql` 로 옮겼다.

**`CATEGORY` 컬럼을 하나 추가했다.** 화면(`NoticeList.jsx`)이 '점검' ·
'안내' · '업데이트' 배지를 이미 그리고 있었는데 표에 자리가 없었다.
없이 옮기면 배지가 빈칸이 된다.

CHECK 는 걸지 않았다. 분류는 운영하면서 늘어나는 값이고, 늘 때마다 DDL 을
고쳐야 하는 제약은 득보다 실이 크다. 화면도 '점검'만 경고색이고 나머지는
기본색이라 모르는 값이 와도 깨지지 않는다.

**쓰기 API 는 만들지 않았다.** `USERS` 에 관리자 구분 컬럼이 없어서
"운영자만 작성"을 가릴 방법이 없다. 로그인만 하면 아무나 공지를 쓸 수 있는
API 를 두느니, 지금은 DB 에 직접 넣는 편이 낫다.

조회수는 목록 GET 에서 올리지 않는다. 화면을 열 때마다 다섯 건이 한꺼번에
오르면 숫자가 뜻을 잃는다. 공지를 펼칠 때 `POST /api/notices/{id}/view` 를
부른다 — 게시판의 `/view` 와 같은 방식이다.

### 게임 종류를 A · B · C 로

`ck_game_histories_type` 이 `'A'` 하나만 허용했는데 화면의 게임은 셋이다.

    A  음식 월드컵   (/game/worldcup)   후보를 둘씩 비교해 좁힌다
    B  취향 밸런스   (/game/balance)    질문 다섯 개로 조건을 만든다
    C  랜덤 돌림판   (/roulette)        운에 맡긴다

글자와 게임의 대응은 `services/game_service.py` 의 `GAME_TYPES` 한 곳에만
적었다. DB 에는 글자만 넣는다 — 표가 '누가 · 무엇을 · 언제'만 남기는
로그라 종류 이름까지 매 행에 넣을 이유가 없다.

**끝난 판이 아니라 시작한 판을 센다.** 세 게임 모두 도중에 나가는 일이
흔하다(월드컵은 일곱 번, 밸런스는 질문 다섯 개를 지나야 끝난다). 끝난 것만
세면 "이 게임을 얼마나 열어보는가"를 알 수 없는데, 지금 알고 싶은 건 그쪽이다.

### 이 표만 모델이 클래스가 아니다

`GAME_HISTORIES` 는 `class X(Base)` 가 아니라 SQLAlchemy Core 의 `Table` 이다.

선언형 모델은 PK 를 반드시 요구한다. "이 객체가 DB 의 어느 행인지"를 PK 로
따라다니기 때문이다. 그런데 이 표에는 PK 가 없다 — 수정도 삭제도 하지 않는
누적 로그라 행 하나를 지목할 일이 없어서 일부러 뺐다.

억지로 `(user_id, created_at)` 을 PK 라고 적어두면 DDL 에 없는 제약을
코드에만 적는 셈이고, 같은 회원이 같은 순간에 두 번 기록되면 SQLAlchemy 가
두 행을 하나로 착각한다. 필요한 건 INSERT 하나뿐이라 객체로 다룰 이유도 없다.

### StrictMode 가 기록을 두 배로 만들던 것

게임 페이지 세 곳이 `useGamePlayLog(gameKey)` 훅 하나를 부른다. 그 안에서
`useRef` 로 한 번만 보내게 막았다.

React 18 이후 개발 모드는 effect 를 일부러 두 번 실행한다. 그대로 두면
개발 중에 게임 기록이 매번 두 줄씩 쌓여서, 실제 사용자 수가 두 배로 보이는
통계가 된다.

기록 실패는 조용히 넘어간다. 놀러 온 사람에게 서버 사정을 알릴 이유가 없다.
Guest 는 아예 부르지 않는다 — `USER_ID` 가 NOT NULL 이라 남길 자리가 없고,
게임 자체는 Guest 도 그대로 할 수 있다.

## 후기 첨부파일 (2026-09-10)

후기에 사진 한 장을 붙일 수 있게 했다. DDL 과 모델은 이미 와 있었고
(`8219edd`), 그 위에 나머지 계층을 얹었다.

### 왜 글쓰기 API 를 안 건드렸나

파일을 붙이는 방법이 두 가지였다.

    A  POST /api/posts 를 multipart 로 바꿔 글과 파일을 한 번에 받는다
    B  POST /api/posts/{id}/file 을 따로 두고 두 번 부른다

**B 를 골랐다.** A 는 요청이 한 번이라 원자적이지만, FastAPI 는 한
엔드포인트에서 `UploadFile` 과 Pydantic 본문을 같이 못 받는다. 필드를
`Form(...)` 으로 풀어써야 하고, 그러면 `PostCreateRequest` 의 검증기
(공백만 든 제목·본문 차단)가 안 돈다. 수정 쪽에도 "파일 유지 / 교체 /
삭제" 를 구분하는 플래그가 붙는다.

B 의 단점인 "중간 상태"는 이 서비스에서 문제가 아니다. 업로드가 실패해도
남는 건 `file_yn='N'` 인 **첨부 없는 멀쩡한 글**이고, 첨부는 원래 선택
사항이라 그게 정상 상태다. 상세 화면에서 사진만 다시 올리면 된다.

덤으로 상세에서 사진만 갈아 끼우는 기능이 공짜로 생겼다.

### 왜 uploads 폴더를 정적 서빙하지 않나

`app.mount("/uploads", StaticFiles(...))` 두 줄이면 끝나는데 안 썼다.

- **삭제된 글의 사진이 계속 열린다.** 정적 서빙은 URL 만 알면 그만이라
  `use_yn='N'` 을 볼 방법이 없다. 지금은 `open_post_file()` 이 살아있는
  글인지 먼저 확인한다
- **원본 파일명을 못 준다.** 디스크에는 UUID 로 저장돼 있어서 그대로
  주면 `a1b2c3....jpg` 가 내려간다. 지금은 `file_org_name` 으로
  "김치찌개.jpg" 를 돌려준다

`attachment` 가 아니라 `inline` 으로 준다. attachment 로 주면 `<img>` 에
넣었을 때 안 그려지고 내려받기 창이 뜬다.

### 파일 이름을 바꿔서 저장하는 이유

사용자가 올린 이름을 그대로 쓰면 두 가지가 깨진다. DDL 주석이 짚어둔 그대로다.

    같은 이름끼리 덮어쓴다     "사진.jpg" 를 두 사람이 올리면 하나가 사라진다
    경로가 섞여 들어온다       "../../.env" 면 서버 파일을 건드린다

그래서 저장은 UUID 로 하고 원래 이름은 보여주기용으로만 따로 적는다.
`absolute_path()` 가 만들어진 경로를 한 번 더 검사한다 — 지금은 경로도
파일명도 서버가 지어낸 값이라 밖으로 나갈 수 없지만, DB 값을 그대로 믿고
파일을 열어주는 코드는 언젠가 반드시 사고가 난다.

### 컬럼 여섯 개를 손으로 만지지 않는다

`ck_reviews_file_set` 이 `file_yn` 과 나머지 다섯 컬럼을 묶어서 본다.
첨부를 뗄 때 `file_yn` 만 'N' 으로 바꾸고 경로를 남겨두면 ORA-02290 이 난다.
그래서 서비스는 모델의 `set_file()` · `clear_file()` 만 부른다.

### 순서에 뜻이 있다

교체할 때는 **새 파일 저장 → DB commit → 옛 파일 삭제** 다.
옛 파일을 먼저 지우면 commit 이 실패했을 때 DB 는 옛 파일을 가리키는데
디스크에는 없다 — 화면에 깨진 이미지가 뜬다.

글을 논리 삭제할 때는 **파일을 안 지운다.** 되살릴 수 있어야 하는데
파일을 지우면 글만 돌아온다.

### 새로 생긴 것

| 계층 | 파일 | 하는 일 |

## 주소로 날씨 보기 (2026-09-09)

회원가입에서 받은 주소가 **저장만 되고 쓰이지 않던 것**을 실제로 연결했다.
화면에는 "사는 곳을 적어두면 그 지역 날씨로 추천해드립니다" 라고 적어놓고
동작은 안 하던 상태였다.

### 좌표를 미리 구워뒀다

"서울특별시 강남구" 를 좌표로 바꾸는 건 바깥 API(Nominatim) 일이고 2~3초 걸린다.
가입할 때마다 부르면 회원가입이 그만큼 느려지고, 그 API 가 죽으면 가입이 막힌다.

그런데 시·군·구는 **목록이 고정이고 좌표도 변하지 않는다.**
그래서 일회성 스크립트로 267개를 한 번만 변환해 `app/data/regions.json` 에
넣어뒀다. 서비스가 돌 때는 표에서 찾기만 한다.

    scratchpad/build_regions.py  ->  regions.json  (저장소에 커밋)

부수 효과가 하나 더 있다. **좌표 변환이 실패한 항목은 지명을 잘못 적었다는 뜻**이라,
목록을 만드는 과정이 곧 검증이 됐다.

### 주소를 드롭다운으로 바꿨다

전에는 시·도 · 시·군·구가 자유 입력이었다. 그러면 `서울시` / `서울특별시` /
`서울` 이 뒤섞이고, **그중 어느 것도 좌표로 바꾸지 못한다.**
목록에서 고르게 하니 이 문제가 사라졌다.

`AddressPicker` 컴포넌트 하나를 회원가입과 마이페이지가 같이 쓴다.
따로 만들면 한쪽만 고쳤을 때 가입 때 고른 주소를 수정 화면에서 못 고르게 된다.

시·도를 바꾸면 시·군·구를 **반드시 비운다.** 안 비우면 "부산광역시 강남구" 같은
있지도 않은 조합이 만들어지고, 서버는 좌표를 못 찾아 기본 좌표로 떨어진다.

### 좌표는 클라이언트가 못 보낸다

`RegisterRequest` · `ProfileUpdateRequest` 에서 `latitude` / `longitude` 를 뺐다.
주소를 받아 **서버가** 좌표로 바꾼다. 클라이언트가 좌표를 직접 보내게 두면
주소와 좌표가 어긋난 회원이 생긴다.

주소를 지우면 좌표도 지운다. 안 그러면 이사한 뒤에도 화면에는 부산이라고
적혀 있는데 서울 날씨가 나온다.

### 날씨 좌표 우선순위

    1) 브라우저가 준 위치        지금 있는 곳이 가장 정확하다
    2) 회원가입 때 고른 주소     위치 권한을 거부했거나 지원 안 하는 브라우저
    3) 기본 좌표(종로2가)        로그인 안 했고 위치도 없을 때

2번이 없던 게 원래 문제였다. 위치 권한을 거부한 사람은 서울에 살든 부산에
살든 영영 종로 날씨를 봤다.

## AI 실연동 — Gemini (2026-09-09)

`AI_PROVIDER=gemini` 로 전환했다. 날씨에 이어 **두 번째로 mock 을 벗은 서비스**다.
Gemini 를 고른 이유는 무료 등급이 있어서다. Claude 경로도 코드에 그대로 남겨뒀다.

### 프로바이더가 셋이 됐다

    mock     카탈로그 39개에서 점수로 고른다 (키 없이 동작)
    gemini   Google Gemini
    claude   Anthropic Claude

**프롬프트와 응답 스키마는 셋이 똑같은 것을 쓴다.** 바꿔 끼웠을 때 추천의
성격까지 달라지면 어느 쪽이 나은지 비교할 수 없다. 다른 건 "그 회사 API 를
어떻게 부르느냐" 뿐이다.

    Claude  도구를 하나 주고 그것으로만 답하게 한다 (tool_choice)
    Gemini  응답 스키마를 직접 넘긴다 (response_schema + response_mime_type)

목적은 같다. 문장이 아니라 정해진 JSON 으로 받는 것.

### 붙이면서 잡은 것

**1. 무료 등급은 모델이 자주 붐빈다 (503)**

`This model is currently experiencing high demand` 가 심심찮게 나온다.
3.4초에 잘 되던 요청이 몇 분 뒤 계속 실패하기도 했다.

두 단계로 막았다.
- 같은 모델로 잠깐(1.5초) 쉬었다 2번 더 시도
- 그래도 안 되면 **예비 모델로 넘어간다**

`GEMINI_MODEL` 에 쉼표로 여러 개를 적는다. `PRICE_PROVIDERS` 와 표기는 같지만
뜻이 다르다 — 가격은 적은 곳을 **전부** 조회하고, 모델은 **하나만** 쓴다.

    GEMINI_MODEL=gemini-3.7-flash,gemini-3.5-flash

429(할당량)도 같이 재시도한다. 분당 제한이면 곧 풀린다.
잘못된 키·없는 모델은 기다려도 안 풀리므로 바로 올린다.

**2. 오류 문구가 영어로 새어나갔다**

원문을 그대로 내보내면 사용자가 못 읽는다. 코드별로 한글 문구를 붙였고,
404 에는 **어느 모델이 문제인지** 이름을 넣었다. 예비 모델까지 있으면
이름이 없을 때 원인을 못 찾는다.

**3. 테스트가 진짜 API 를 부르기 시작했다**

`.env` 를 gemini 로 바꾸자 `ai_api.recommend_foods()` 를 부르던 테스트가

- `conftest.py` 에 autouse 픽스처를 두어 **테스트 중에는 항상 mock**
- 단위 테스트는 분기 함수가 아니라 `mock_recommend_foods()` 를 직접 호출

진짜 AI 응답이 스키마에 맞는지는 테스트가 아니라 실제로 한 번 불러서 볼 일이다.

## 설계 결정 — 테이블을 안 늘리기 위해 한 것들

"테이블은 7개로 고정한다"를 지키려면 갈 곳이 없는 데이터가 네 종류 있었다.
각각을 어디에 뒀는지와 그 대가를 적는다.

### 1. AI 추천 기록 → 브라우저 (localStorage)

`/ai-history` 화면은 "언제 어떤 조건으로 뭘 추천받았는지"를 보여준다.
추천 후보를 DB에 저장하지 않는다는 원칙(§13)과 정면으로 부딪힌다.

**메뉴 이름과 조건 문장만** localStorage 에 남기기로 했다(`AiLogContext`).
레시피 본문은 저장하지 않고, 다시 열면 AI가 새로 만든다.

- 대가: 브라우저를 바꾸면 기록이 안 따라온다.
- 여러 기기에서 보이게 하려면 테이블이 하나 필요하다. 그건 설계를 바꾸는
  결정이라 지금 하지 않았다.

### 2. 찜한 레시피 → 브라우저 (기존 유지)

이름만 저장한다. 그래서 `/liked` 는 카드가 아니라 이름 목록이다.
조리시간·가격을 같이 보여주려면 찜한 개수만큼 AI 호출이 필요한데,
목록을 여는 데 그만한 시간을 쓸 이유가 없다.

### 3. 알림 → 조회할 때 만들어 낸다

`GET /api/users/me/notifications` 는 알림 테이블을 읽지 않는다.
**내 글에 달린 댓글**과 **내 글이 받은 좋아요**를 JOIN 해서 그 자리에서 만든다.

- 별도 테이블을 두면 "댓글을 지웠는데 알림만 남는" 문제를 또 관리해야 한다.
- 읽음 여부는 서버가 모른다. "마지막으로 종을 연 시각"만 브라우저에 저장하고
  (`ProfileContext`) 그보다 나중에 생긴 것을 안 읽음으로 센다.
- 내가 내 글에 단 댓글과 내가 누른 좋아요는 뺀다.

### 4. 요리 레벨 → 컬럼이 아니라 계산

`level` · `exp` 컬럼을 만들면 "글 쓸 때 +30" 같은 갱신을 기능마다 흩어놔야
하고, 한 곳만 빠뜨려도 값이 조용히 어긋난다.
확정한 식사 · 글 · 댓글 · 받은 좋아요는 이미 테이블에 다 있으므로 조회할 때 센다.

```
EXP = 요리 50 + 글 30 + 댓글 10 + 받은 좋아요 5
레벨업 필요량 = 100, 150, 200, ... (레벨마다 +50)
칭호 = 입문(1) · 초보(5) · 중수(10) · 고수(20) · 장인(30)
```

규칙을 바꾸면 과거 데이터가 자동으로 따라온다. 대신 `/api/users/me` 는
COUNT 쿼리가 네 번 돈다. 그래서 새로고침마다 부르는 `/api/auth/me` 와
**분리해 뒀다** — 그쪽은 토큰 확인용이라 가벼워야 한다.

`recommend_count`(사이드바 "추천 완료")만 서버가 모른다.
추천을 저장하지 않기 때문이다. 그건 브라우저의 AI 추천 기록 개수를 쓴다.

### 5. 카테고리 · 게임 · 공지 → 서버 파일

사용자가 만드는 값이 아니라 테이블을 만들 이유가 없고, 프론트에 두면
백엔드(AI 프롬프트)와 프론트(화면)가 서로 다른 목록을 들고 있게 된다.
실제로 냉장고 재료 칩의 글자가 서버가 아는 재료 이름과 어긋나면
아무것도 매칭되지 않는데 화면만 봐서는 이유를 알 수 없다.

`backend/app/data/catalog.json` 한 곳에서 관리하고 `GET /api/catalog` 로 내려준다.

## AI 연동 (STEP 10~11)

### Structured Output

`tools` 에 함수 하나를 알려주고 `tool_choice` 로 "반드시 이걸 써서 답해라"고
시킨다. 그러면 답이 문장이 아니라 스키마 모양의 JSON 으로 온다.
자유 텍스트로 받으면 줄바꿈 하나만 달라져도 파싱이 깨진다.

### 알레르기는 프롬프트만으로 막지 않는다

프롬프트에 "땅콩은 절대 넣지 마세요"라고 적어도 AI가 지키지 않을 수 있다.
못 지켰을 때의 결과가 심각한 조건이라, **받은 답을 서버가 한 번 더 검사해서
걸러낸다**(`ai_service.ask_ai`). 프롬프트는 부탁이고, 이 검사가 실제 방어선이다.

`DISLIKE` 는 다르게 다룬다. 빼지 않고 순위만 뒤로 미루고,
레시피에서는 `substitutes` 에 대체안을 함께 적는다.

### 예산은 생성 단계에서 제한한다

만들어놓고 걸러내면 후보가 0건이 되기 쉽다. 프롬프트에 상한을 넣고,
그래도 0건이면 예산을 3,000원 넓혀 **한 번만** 다시 물어본다.
"8천원 이하로는 없습니다" 대신 가장 가까운 대안을 준다.

### mock 프로바이더

`AI_PROVIDER=mock` 이 기본값이다. 카탈로그의 음식 39종에서 조건에 맞는 것을
골라 점수를 매긴다. **랜덤을 쓰지 않는다** — 같은 조건이면 늘 같은 결과가
나와야 화면 버그를 잡을 수 있다. 분량·가격은 재료명의 md5 에서 만든다
(파이썬 내장 `hash()` 는 서버를 다시 켤 때마다 값이 바뀐다).

검색어가 있으면 날씨 점수를 아예 안 본다. "매운 국물요리"를 찾았는데
더운 날이라고 냉면이 위로 오면 검색이 고장 난 것처럼 보이기 때문이다.

## 가격 비교 (STEP 17~19)

응답 모양은 프론트 `PriceTable` 이 기대하는 그대로다.

```json
[{ "name": "돼지고기 200g",
   "offers": [{ "shop": "서울 가락시장", "price": 11400, "link": "..." }] }]
```

  전체가 죽으면 안 된다.

## 인기 레시피 기간 집계

`review_likes.created_at` 이 기준이고, **그 기간에 새로 눌린 좋아요만** 센다.

## 논리 삭제에서 서비스 계층이 책임진 것

FK 의 `ON DELETE CASCADE` 와 참조 차단은 진짜 `DELETE` 에만 작동한다.
`UPDATE use_yn='N'` 은 DB 입장에서 그냥 값 수정이라 아무 반응도 없다
(`db/01_schema.sql` 상단 [4]). 그래서 아래 둘을 코드가 막는다.

- **회원 탈퇴** — 그 사람의 글 · 댓글 · 좋아요 · 기록 · Ban 도 함께 `'N'`
  (`user_service.withdraw`). 안 하면 탈퇴한 사람의 글이 게시판에 계속 남는다.
- **살아있는 후기가 달린 기록 삭제 차단** — 409 로 막는다
  (`history_service.delete_history`). 기록이 사라지면 게시글의 레시피가
  통째로 비기 때문이다(게시글은 복사본을 안 두고 JOIN 해서 읽는다).

탈퇴 후 토큰은 따로 무효화하지 않는다. JWT 는 발급 목록을 서버가 들고 있지
않아 취소할 방법이 없다. 대신 `core/deps.py` 가 요청마다 `use_yn` 을
확인하므로 남은 토큰으로는 아무것도 못 한다.

## 추가 확정된 요구사항 (2026-08-17)

프론트 화면은 하드코딩 데이터로 이미 만들어뒀다. 백엔드에서 채울 부분만 적는다.

### 1. 좋아요 받은 레시피 — 기간 검색 (대시보드)

- 기본값: **오늘 포함 최근 30일**
- 사용자가 시작일~종료일을 직접 고르면 그 기간에 좋아요를 받은 목록만 표시
- 프론트: `components/common/DateRangeFilter.jsx`, 화면은 `HomePage`

**서버에서 할 일**
```sql
-- post_likes.created_at 기준. 양 끝 포함
WHERE pl.created_at >= :start AND pl.created_at < :end + 1
```
- `created_at`은 **UTC로 저장**돼 있다. 화면에서 고른 날짜는 KST 기준이므로
  경계에서 9시간이 어긋난다. 서버에서 KST -> UTC 변환 후 비교할 것
- 정렬은 좋아요 수 내림차순. 기간이 넓으면 페이징 필요

### 2. 예산 안에서 레시피 추천

- 사용자가 금액(예: 8000원)을 입력하면 **그 금액 이내로 만들 수 있는 레시피만** 추천
- 프론트: `components/recommendation/BudgetFilter.jsx`

**서버에서 할 일**
- AI 프롬프트에 예산 상한을 넣어 **생성 단계에서** 제한한다.
  생성 후 걸러내면 후보가 0건이 되는 경우가 잦다
- 예산을 못 맞추면 "가장 가까운 금액" 대안을 함께 내려줄 것

### 3. 최저가 / 최고가 비교

- 재료 하나당 **시장별 소매 조사가격**을 모은다 (KAMIS 는 시장·등급별로 여러 행)
- 가장 싼 곳과 가장 비싼 곳을 나란히 보여주고, 합계도 구간으로 표시
- 프론트: `components/price/PriceTable.jsx` (`getPriceSummary()`로 합계 계산)

**응답 형태** — 프론트가 이 모양을 기대한다
```json
[
  { "name": "돼지고기 앞다리살 200g",
    "offers": [
      { "shop": "서울 가락시장", "price": 3980, "unit": "1kg",
        "link": "...", "surveyed_at": "20260908" },
      { "shop": "부산 엄궁시장", "price": 4350, "unit": "1kg",
        "link": "...", "surveyed_at": "20260908" }
    ] }
]
```
- `.env`의 `PRICE_PROVIDERS`를 앞에서부터 시도하고, 값이 나오면 멈춘다
  (합치면 단위 기준이 다른 값이 한 표에 섞인다)
- 값을 지어내던 mock 프로바이더는 제거했다. KAMIS 는 농수산물만 조사하므로
  두부·간장 같은 가공식품은 **가격 정보 없음**으로 두고, 합계에 몇 개를
  더한 값인지 함께 적는다
- 쇼핑몰 최저가가 아니라 **시장 조사가격**이다. 구매 링크가 없고, 단위와
  조사일자를 같이 적어야 한다. 화면에 주의 문구를 넣어뒀다
- 조사일자가 필수 파라미터인데 주말·공휴일은 조사가 없다. 일주일치를 받아와
  **가장 최근 조사일자만** 남긴다 (`latest_rows()`). 안 그러면 최저/최고가
  시장 차이가 아니라 날짜 차이가 된다
- 구분코드는 소매(01)만 쓴다. 중도매(02)와 섞으면 단가 기준이 달라 뒤죽박죽된다

### 요즘 싼 재료 추천 (services/bargain_service.py)

- KAMIS 품목 101개의 가격 흐름을 훑어 값이 내린 재료를 고르고,
  그 목록을 제미나이에게 넘겨 "싼 재료로 만드는 메뉴" 를 받는다
- 대시보드에 날씨 추천과 나란히 놓인다. 날씨가 "오늘 어떤 날인가" 로
  고른다면 이쪽은 "요즘 뭐가 싼가" 로 고른다. 축이 다르다
- **쇼핑몰 API 로는 못 만드는 기능이다.** 네이버·11번가·쿠팡은 "지금 얼마"
  만 준다. 일별 조사값이 있어야 "요즘 싼지" 를 말할 수 있다

**초당 요청 제한에 걸렸던 일** — 훑기를 동시에 두 번 돌렸다가 101개가
거의 전부 막혔다(HTTP 429). 서버 시작 시 미리 훑는 작업과 사용자 요청이
겹친 것이다. 세 가지로 막았다.

    잠금       훑기는 한 번에 하나만 돈다 (scan_lock)
    속도 조절  동시 2개 + 요청 사이 0.15초. 56초 걸리지만 안 막힌다
    파일 저장  같은 날 훑어둔 게 있으면 읽고 넘어간다 (0.02초)

파일(`app/data/bargains.json`)은 커밋해도 된다. KAMIS 는 공공데이터라
저장·공유 제한이 없고, 팀원이 인증키 없이도 실제 시세를 볼 수 있다.
(11번가는 약관 제6조 ④ 로 데이터 저장이 금지라 이렇게 못 한다.)

### 가격 추이 (integrations/price_api.py)

- "양파 지난주보다 9% 쌈" 을 재료명 옆 배지로 보여준다
- **추가 호출이 없다.** 조사일자가 필수 파라미터라 이미 일주일치를 받아놓고
  최근 하루만 쓰고 버리고 있었다. 버려지던 데이터로 만든다
- 받아온 기간의 처음 날과 마지막 날의 전국 평균을 견준다. 주말·공휴일은
  조사가 없어 날짜가 띄엄띄엄해서, "7일 전" 을 딱 집지 않는다
- 5% 미만은 알리지 않는다. 시장가는 며칠 사이에도 1~2% 씩 흔들려서,
  다 알리면 배지가 늘 떠 있어 아무 뜻이 없어진다
- **쇼핑몰 API 로는 못 만드는 값이다.** 그쪽은 지금 값만 준다.
  KAMIS 가 일별 조사값이라 가능한 일이고, 이 서비스의 차별점이다

### 레시피 캐시 (services/ai_service.py)

- 같은 음식·같은 Ban 조합이면 6시간 동안 AI 를 다시 부르지 않는다
- **31초 → 3초.** 제미나이가 붐비면 예비 모델로 넘어가느라 30초를 넘길 때가 있다.
  발표 리허설에서 같은 요리를 여러 번 여는데, 두 번째부터는 기다림이 없다
- **가격은 캐시하지 않는다.** 조회 시점의 값이라 6시간 전 값을 오늘 값으로
  보여주면 안 된다 (설계 원칙 §13). 저장할 때 `prices` 를 비운다
- 꺼낼 때 복사본을 준다. 원본을 그대로 주면 부르는 쪽이 채운 가격이
  캐시에 눌어붙어 다음 사람에게 남의 조회 결과가 나간다
- Ban 을 열쇠에 넣는다. 이름만으로 묶으면 돼지고기 알레르기가 있는 사람에게
  돼지고기가 든 레시피를 보여주게 된다
- 네이버 쇼핑 검색 API(2026-07-31 종료)를 KAMIS 로 교체했다. 쿠팡·11번가는
  제휴 승인이 필요해 보류
- 세 곳을 순차 호출하면 느리다. `httpx.AsyncClient`로 **병렬 호출**할 것

## 화면 개편 (2026-08-24) — 대시보드 시안 반영

> **`mocks/` 폴더는 2026-09-09에 삭제했다.** 아래에 "서버가 채워야 할 부분"으로
> 적어둔 것들은 전부 API로 옮겼다. 찜 목록과 AI 추천 기록만 의도적으로
> 브라우저에 남겼다(위쪽 「설계 결정」 참고).

시안(`현재UI.png`)에 맞춰 프론트를 다시 짰다. 여기 적는 건 서버가 채워야 할 부분이다.

### 새로 생긴 화면

| 경로 | 화면 | 서버가 할 일 |
|---|---|---|
| `/game`, `/game/worldcup`, `/game/balance` | 메뉴 게임 3종 | 후보 목록만 내려주면 된다. 진행은 화면에서 한다 |
| `/search?q=` | 레시피 검색 | 검색어를 **그대로 AI에 넘긴다**. "8천원 이하 파스타" 같은 문장 해석이 목적이라 SQL LIKE로는 안 된다 |
| `/fridge` | 냉장고 재료로 찾기 | 고른 재료를 프롬프트에 넣어 만들 수 있는 메뉴만 생성. 만들어놓고 거르면 0건이 되기 쉽다 |
| `/ai-history` | AI 추천 기록 | 언제·어떤 조건으로·무엇을 받았는지. 레시피 본문은 저장하지 않는다(§13 원칙 유지) |
| `/settings` | 설정 | 없음. 테마·알림은 브라우저 localStorage에만 둔다 |
| `/liked` | 찜한 레시피 | 찜 테이블이 필요하다. 지금은 `food_name` 배열을 localStorage에 둔다 |
| `/popular` | 인기 레시피 전체 | 기존 "좋아요 받은 레시피"의 이름을 바꾼 것 |

`/liked`가 **찜한 레시피**(내가 담은 것)로 바뀌었고, 남들이 많이 누른 목록은
`/popular`로 갈라졌다. 대시보드 오른쪽 순위가 후자다.

### 서버에서 채울 값

- **요리 레벨** (`MOCK_PROFILE`) — `GET /users/me` 응답에 `level` `title` `exp`
  `exp_next` `streak_days` `recommend_count` `cook_count` 를 함께 싣는다.
  퍼센트로 계산해서 내리지 말 것. 화면마다 필요한 표현이 다르다
- **알림** (`MOCK_NOTIFICATIONS`) — 읽음 여부(`read`)가 상단바 배지 숫자가 된다
- **인기 레시피 기간 집계** — 지금은 화면에서 거른다. 기간 안에 **새로 눌린**
  좋아요만 세야 한다. 누적으로 세면 오래된 글이 영원히 1위다
- **음식별 주재료** (`MOCK_FOOD_INGREDIENTS`) — 냉장고 찾기 매칭용

### 다크 모드

`<html data-theme="dark">` 한 곳만 바뀌고 색은 전부 `styles/index.css`의
CSS 변수에서 갈린다. **컴포넌트 CSS에 색상 리터럴(`#fff` 등)을 새로 적지 말 것.**
적는 순간 그 자리만 라이트 모드로 남는다. 흰 배경 위에 얹는 하트 버튼처럼
의도적으로 고정한 곳에는 주석을 달아뒀다.

첫 페인트 전에 테마를 정하려고 `index.html`에 인라인 스크립트를 하나 뒀다.
React가 뜬 뒤에 칠하면 다크 모드 사용자에게 흰 화면이 한 프레임 번쩍인다.

## 난이도 낮추기 마무리 — 잔여 4건 (2026-09-06)

전수 점검을 다시 돌려 **손대지 않고 남아 있던 곳**을 정리했다.
앞선 세 차례 작업(백엔드 · 프론트엔드 · 스타일 통일)에서 빠진 파일들이다.

### 고친 것

| 파일 | 무엇 | 전 | 후 |
|---|---|---|---|
| `routers/bans.py` | 리스트 컴프리헨션 (프로젝트 마지막 1곳) | `[BanResponse.model_validate(b) for b in bans]` | `for` 루프 + `append` |

`health.py` 와 `format.js` 는 앞선 작업에서 **한 번도 열지 않은 파일**이었다.

### `?.` 와 `??` — 없애지 않고 문서로 뺐다

프론트엔드 24개 파일에 58곳 쓰인다. 정책이 문서에 없어서 이번에 정했다.

**없애지 않는다.** 없애면 `if` 문 8줄이 되어 오히려 어려워지고,
안 쓰면 서버 응답이 비었을 때 리액트 화면이 통째로 하얘진다.

대신 [`STUDY_JS_SYNTAX.md`](STUDY_JS_SYNTAX.md) 를 새로 썼다.
`?.` · `??` 두 개만 다루고, **`||` 와 `??` 의 차이**(`0` 과 빈 문자열을
기본값으로 바꾸느냐)를 표로 정리했다.

소스에는 헷갈리는 3곳에만 주석을 더 넣었다. 같은 설명을 58번 적으면
그게 더 읽기 어렵다.

- `api/client.js` — 문서 위치를 적어뒀다 (모두가 제일 먼저 여는 파일)
- `Roulette.jsx` — `?.(` 는 속성이 아니라 **함수 호출**을 건너뛰는 모양이다
- `RecommendPage.jsx` — 여기만 `??` 가 아니라 `||` 다. 이유를 안 적으면 실수로 보인다

## 남은 파일 마무리 — 스타일 통일 (2026-09-06)

앞선 작업은 "어려운 문법이 있는 파일"만 골라서 고쳤다.
그러다 보니 손댄 파일과 안 손댄 파일의 **스타일이 섞여버렸다.**
한 프로젝트 안에 두 가지 방식이 있으면 초보에게는 오히려 더 헷갈린다.

### 무엇을 통일했나

| 무엇 | 전 | 후 |
|---|---|---|
| 이벤트 핸들러 선언 | `const onSubmit = (e) => {...}` (22곳) | `function onSubmit(e) {...}` (전부) |
| `alive` 플래그 | 파일마다 있기도 없기도 | 아래 규칙으로 정리 |

손댄 파일 17개: TopBar · Sidebar · CategoryBar · DateRangeFilter · BudgetPicker ·
BudgetRange · FoodFinder · Roulette · MainLayout · MyPage · SettingsPage ·
CommunityPage · HistoryPage · RecipePage · LoginPage · RegisterPage · PostWritePage

### `alive` 플래그 — 지운 곳과 남긴 곳

똑같아 보이지만 하는 일이 다르다.

**지웠다 (HistoryPage · MyPage)**
의존성이 `[]` 라서 화면이 열릴 때 한 번만 실행된다.
플래그가 막아주는 건 "화면을 떠난 뒤 도착한 응답"뿐인데,
리액트 18부터는 그때 setState 를 불러도 아무 일도 안 일어난다. 읽을 거리만 늘린다.

**남겼다 (CommunityPage)**
의존성이 `[keyword]` 라서 **검색어를 고칠 때마다 다시 실행된다.**
요청은 보낸 순서대로 도착하지 않는다. "김" 의 응답이 "김치" 의 응답보다 늦게 오면
화면에 "김치" 결과가 떴다가 "김" 결과로 덮인다.
이건 실제로 나는 버그라 플래그가 꼭 필요하다. 대신 왜 필요한지 주석에 풀어 적었다.

> 같은 코드라도 의존성 배열이 `[]` 인지 `[무언가]` 인지에 따라 필요/불필요가 갈린다.

|---|---|

| `mocks/index.js` (1,421줄) | 순수 데이터 |
| `styles/**/*.css` | 이번 작업 범위가 아니다 |

### 검증하다 잡은 것

## 프론트엔드 코드 난이도 낮추기 (2026-09-06)

백엔드에 이어 리액트 쪽도 같은 기준으로 정리했다.
**화면 동작과 API 호출은 그대로다.** 문법과 구조만 손봤다.

### 무엇을 바꿨나

| 무엇 | 전 | 후 |
|---|---|---|
| `api/client.js` | 모듈 전역 `authToken` + `setAuthToken()` 으로 동기화 | 요청할 때 `getToken()` 으로 localStorage 에서 바로 읽음 |

### 남긴 것과 이유

- **`{ ...prev, [name]: value }`** — 리액트 폼의 기본 패턴이라 없앨 수 없다.
  대신 대괄호가 무슨 뜻인지 주석으로 풀어 적었다.
- **`api/client.js` 의 인터셉터** — 토큰을 화면마다 붙이지 않으려면 필요하다.
- **`onTokenExpired` 콜백 하나** — `client.js` 가 `AuthContext` 를 직접 import 하면
  순환 참조가 된다. 왜 이 방향인지 주석에 적어뒀다.
- **`PostDetailPage` 의 낙관적 갱신** — 하트가 즉시 반응해야 눌린 느낌이 난다.

### 작업 중 잡은 버그

`PostDetailPage` 좋아요를 함수형 업데이트(`setLikeCount(n => n + 1)`)에서
직접 값 계산으로 바꾸다가, **실패 시 되돌리는 값이 1 어긋나는** 문제를 만들었다가 잡았다.
누른 순간의 값을 `previousLiked` / `previousCount` 에 먼저 담아두고
실패하면 그 값으로 되돌리는 방식으로 고쳤다 — 결과적으로 원본보다 읽기도 쉽다.

## 스키마 v2 (2026-09-04) — 논리 삭제 · 후기 게시판 FK

### 무엇이 바뀌었나

| # | 변경 | 이유 |
|:--:|---|---|
| 1 | 6개 테이블에 `USE_YN CHAR(1)` 추가 | 삭제 · 탈퇴를 물리 삭제 대신 `'N'` 갱신으로 |
| 2 | `UNIQUE` 제약 4개 → 함수 기반 UNIQUE 인덱스 | `'N'` 행이 자리를 차지해 재등록이 막히는 것을 방지 |
| 3 | `POSTS` → `RECIPE_REVIEWS` | "레시피 추천" 게시판이라는 성격을 이름에 반영 |
| 4 | `RECIPE_REVIEWS`에 `MEAL_HISTORY_ID` 합성 FK 추가 | 직접 만들어본 요리만 후기를 쓸 수 있게 DB가 강제 |
| 5 | `POST_LIKES` → `REVIEW_LIKES`, `COMMENTS` → `REVIEW_COMMENTS` | `post_id` → `review_id` |
| 6 | `USERS`에 `GENDER` + 주소 4개 컬럼 추가 | 대시보드 첫 화면의 날씨 조회 (STEP 12) |

`VERIFICATION_CODES`에는 `USE_YN`을 붙이지 않았다. OTP는 사용자가 삭제하는
데이터가 아니고 `used_at` / `expires_at`으로 이미 생명주기를 관리한다.

### 왜 UNIQUE를 인덱스로 바꿨나

논리 삭제에서 가장 먼저 터지는 곳이다. `uq_post_likes(user_id, post_id)`가
평범한 UNIQUE면, 좋아요를 취소(`'N'`)한 뒤 다시 누르는 순간 `ORA-00001`이 난다.
행이 그대로 남아 있기 때문이다. 같은 문제가 Ban 재등록 · 탈퇴 이메일 재가입에도 있다.

```sql
CREATE UNIQUE INDEX uq_review_likes ON review_likes (
    CASE WHEN use_yn = 'Y' THEN user_id   END,
    CASE WHEN use_yn = 'Y' THEN review_id END
);
```

`'N'` 행은 모든 키 컬럼이 `NULL`이 되어 인덱스에 들어가지 않는다.
살아있는 행끼리만 유일성을 본다.

**대신 이 인덱스는 `WHERE user_id = :v` 조회에 쓰이지 않는다.** 선두가 표현식이라
옵티마이저가 매칭하지 못한다. 그래서 조회용 일반 인덱스를 `(col, use_yn)`으로
따로 만들었다. `idx_users_email` · `idx_user_bans_user` · `idx_review_likes_review`가 그것이다.

### 왜 합성 FK인가

```sql
CONSTRAINT fk_reviews_meal FOREIGN KEY (meal_history_id, user_id)
                           REFERENCES meal_histories (id, user_id)
```

`meal_history_id` 하나만 참조하면 "존재하는 히스토리"인 것만 보장되고,
**남의 히스토리를 자기 후기로 공유하는 것**은 막지 못한다. 쌍으로 걸면
글쓴이와 히스토리 주인이 다를 때 DB가 `ORA-02291`로 거부한다.
Oracle은 PK/UNIQUE 조합만 참조 대상으로 허용하므로
`meal_histories`에 `uq_meal_id_user UNIQUE (id, user_id)`를 함께 넣었다.

### FK로 못 막는 것 — 서비스 계층의 책임

`ON DELETE CASCADE`와 참조 차단은 **진짜 `DELETE`에만 작동한다.**
`UPDATE use_yn='N'`은 DB 입장에서 그냥 값 수정이라 아무 반응도 없다. 그래서:

- **회원 탈퇴** — `users`만 `'N'`으로 바꾸면 그 사람의 후기 · 댓글 · 좋아요는
  `'Y'`로 남아 화면에 계속 보인다. 하위 테이블까지 연쇄 UPDATE 해야 한다. **(미구현)**
- **"후기가 있으면 히스토리 삭제 금지"** — 논리 삭제는 FK가 못 막는다.
  `'N'`으로 바꾸기 전에 살아있는 후기가 있는지 검사해야 한다. **(미구현)**

### 실측으로 확인한 것 (25건 중 24건 통과, 1건은 테스트 쪽 오류)

| 확인한 동작 | 결과 |
|---|---|
| 남의 히스토리로 후기 작성 | `ORA-02291` 거부 ✅ |
| 같은 식사로 후기 2번 | `ORA-00001` 거부 ✅ |
| 후기 삭제(`'N'`) 후 같은 식사로 재작성 | 성공 ✅ |
| 좋아요 취소 후 재클릭 | 성공 ✅ |
| Ban 해제 후 같은 재료 재등록 | 성공 ✅ |
| 탈퇴 후 같은 이메일 재가입 | 성공 ✅ |
| 재가입 계정이 살아있는 동안 탈퇴 계정 복구 | `ORA-00001` 거부 (정상) ✅ |
| 후기가 달린 히스토리 `DELETE` | `ORA-02292` 거부 ✅ |
| 후기가 달린 **회원** `DELETE` | **통과됨.** 연쇄 삭제가 `recipe_reviews`를 먼저 지워서 막히지 않는다. `DELETE FROM users`를 손으로 실행하면 그 회원의 모든 데이터가 사라진다 ⚠️ |

## 설계 결정 기록

### 왜 CSS를 styles/ 아래로 몰았나 (2026-08-23)
JSX와 CSS가 한 폴더에 섞여 있어 `pages/`를 열면 파일 수가 두 배로 보였다.
`src/styles/` 아래에 **소스 폴더 구조를 그대로 미러링**해서 옮겼다.

```
src/pages/LoginPage.jsx           -> import '../styles/pages/LoginPage.css'
src/components/common/TopBar.jsx  -> import '../../styles/components/common/TopBar.css'
```

`src/styles/index.css`는 전역이라 그대로 뒀다.
CSS 파일을 새로 만들 때도 이 규칙을 따를 것. 클래스명 규칙(BEM 풍의
`.mypage__ban-name`)은 바뀐 게 없다.

### 왜 Ban 추가는 사전 조회 없이 IntegrityError만 잡나
회원가입(`register_user`)은 이메일/닉네임 **두 개**의 UNIQUE가 있어서, 어느 쪽이
중복인지 알려주려고 사전 `SELECT`를 한 번 한다. Ban은 `uq_user_bans` 하나뿐이라
`IntegrityError`가 곧 "재료명 중복"이다. 사전 조회를 넣어봐야
SELECT-INSERT 사이의 경합은 못 막으면서 쿼리만 늘어난다.

### 왜 남의 Ban을 지우려 하면 403이 아니라 404인가
403은 "권한은 없지만 그 리소스는 존재한다"는 뜻이 된다. id를 1씩 올려가며
403/404를 세면 남의 Ban이 몇 개인지 알 수 있다. 없는 id와 남의 id를 같은 404로
묶어서 그 차이를 없앴다.

### 왜 재료명을 스키마에서 `strip()` 하나
`'오이'`와 `'오이 '`는 다른 문자열이라 `uq_user_bans`가 중복으로 보지 않는다.
DB에 닿기 전에 잘라내야 UNIQUE 제약이 의도대로 동작한다. 회원가입 닉네임과 같은 이유다.

### 왜 PostgreSQL에서 Oracle로 바꿨나
프로젝트 방침 변경. 전환 시점에 SQLAlchemy 모델을 하나도 안 만든 상태여서
비용이 거의 없었다. 영향 파일은 5개뿐이었고 프론트엔드는 수정 0건.

### 왜 change 단계에서 코드 행을 지우나
`used_at`이 찍힌 코드는 `verify`를 다시 통과하지 못하지만, `change`는
"`used_at`이 있는가"를 조건으로 삼기 때문에 같은 코드로 몇 번이든 호출할 수 있다.
비밀번호를 바꾼 뒤 행을 삭제해서 그 구멍을 막는다.

### 왜 `verification_codes.used_at` 컬럼을 뒀나
`verify-code`와 `change`가 별도 엔드포인트라, 인증 성공 사실을 어딘가 남겨야
`change` 단계에서 "검증된 요청"인지 판별할 수 있다. 없으면 같은 코드로
비밀번호를 여러 번 바꿀 수 있다(OTP 일회성 위반).

### 왜 JSON을 CLOB에 넣나
Oracle 21c에 네이티브 `JSON` 타입이 있지만 **SQLAlchemy 2.0.52의 Oracle
dialect가 지원하지 않는다** (`visit_JSON` 미구현 → `CompileError`).
`CLOB` + `CHECK (... IS JSON)`이 유일하게 성립하는 선택지.
레시피 JSON은 통째로 읽고 쓰는 스냅샷이라 성능 손실도 무의미하다.

### 왜 passlib 대신 bcrypt를 직접 쓰나
passlib 1.7.4는 2020년 이후 릴리스가 없어 bcrypt 5.x와 호환되지 않는다.
`AttributeError: module 'bcrypt' has no attribute '__about__'`.

### 왜 로그인 실패 시 남은 횟수를 알려주나
사용성을 위해 그렇게 정했다 (2026-08-17).

단, 이건 트레이드오프다. `(남은 시도 N회)` 문구는 **존재하는 계정에만** 붙으므로,
없는 이메일과 응답을 비교하면 가입 여부를 알아낼 수 있다.
"없는 이메일과 틀린 비밀번호를 구분하지 않는다"는 로그인 정책이 이 부분에서는
사실상 무력해진다.

계정 열거를 막는 쪽으로 바꾸려면 `login_user()`의 401 메시지를
`_INVALID_CREDENTIALS` 상수로 되돌리면 된다. 그 한 줄이 전부다.

### 왜 좋아요/댓글 수를 컬럼으로 안 두나
MVP에서는 `COUNT()` 집계로 충분하다. 비정규화 컬럼은 동기화 버그 위험이
성능 이득보다 크다.

## ⚠️ Oracle 관련 함정 (실측으로 확인한 것들)

앞으로 코드 쓸 때 계속 걸리는 것들이라 기록해둔다.

### 1. `VARCHAR2(n)`은 바이트 단위다
```sql
VARCHAR2(50)        -- 한글 16자에서 잘림 (DB가 BYTE 시맨틱)
VARCHAR2(50 CHAR)   -- 한글 50자 정상        <- 반드시 이렇게
```
이 DB의 `NLS_LENGTH_SEMANTICS`는 `BYTE`다. SQLAlchemy는 자동으로 `CHAR`를
붙여주지만, 수기 DDL에서는 직접 써야 한다.

### 2. 타임존이 조용히 어긋난다 (가장 위험)
python-oracledb는 tzinfo를 **저장·조회 양방향에서 버린다.**
```
바인딩: 08:00+00:00 (UTC)  ->  DB 저장: 08:00 +09:00   ← 9시간 오차, 에러 없음
조회  : DB의 +09:00 값      ->  파이썬: tzinfo=None
```
**대응**: DB에는 UTC만 저장한다.
- DDL: `TIMESTAMP(6) DEFAULT SYS_EXTRACT_UTC(SYSTIMESTAMP)`
- 모델: `models/types.py`의 `UtcTimestamp` 타입 사용 (경계에서 변환)
- 커넥션: 접속 시 `ALTER SESSION SET TIME_ZONE='+00:00'` (database.py)

### 3. 빈 문자열이 NULL이다
`''`를 `NOT NULL` 컬럼에 넣으면 `ORA-01400`으로 500이 난다.
Pydantic 스키마에 `min_length=1`을 반드시 건다.

### 4. `SELECT 1`이 안 된다
Oracle은 FROM 절이 필수다. `SELECT 1 FROM DUAL`.

### 5. DBeaver가 빈 줄에서 SQL을 자른다
`CREATE TABLE` 안에 빈 줄이 있으면 문장이 쪼개져 `ORA-00900`이 난다.
DDL 파일은 이미 빈 줄을 제거해뒀다.
설정으로도 끌 수 있다: Preferences → Editors → SQL Editor → SQL Processing
→ "Blank line is statement delimiter" → Never

### 6. `ON CONFLICT` / `ILIKE`가 없다
- 중복 INSERT: `MERGE` 또는 `IntegrityError` 캐치 (STEP 22 좋아요에서 필요)
- 대소문자 무시 검색: `LOWER(col) LIKE LOWER(:kw)` (STEP 20 게시판 검색)

### 7. `DROP TABLE IF EXISTS`가 없다
21c에는 없다(23ai부터). `db/00_drop_all.sql`처럼 PL/SQL로 우회.

### 8. bcrypt는 72바이트가 상한이다
한글 비밀번호는 24자가 최대. `schemas/auth.py`에서 바이트 기준으로 검증한다.

### 9. 리스너가 설치 시점의 IP에 고정된다 (개인 PC 설치 시)
XE를 설치하면 `listener.ora`에 그 순간의 IP가 박힌다.
```
(ADDRESS = (PROTOCOL = TCP)(HOST = 192.168.219.101)(PORT = 1521))
```
이러면 `localhost` 접속이 거부된다 — `DPY-6005` / `WinError 10061`.
서비스는 Running이고 DBeaver가 IP로 붙으면 되기 때문에 원인을 찾기 어렵다.

**대응**: `<ORACLE_HOME>/network/admin/listener.ora`에서 `HOST`를 `0.0.0.0`으로
바꾸고 `OracleOraDB21Home1TNSListener` 서비스를 재시작한다.
IP를 직접 적으면 다른 네트워크(집↔학원)로 이동할 때마다 다시 깨진다.

확인: `Get-NetTCPConnection -State Listen -LocalPort 1521` 이 `0.0.0.0`을 보여야 한다.

## ⚠️ Windows 개발환경 함정

### 1. pip가 requirements.txt를 cp949로 읽는다
한글 Windows에서 pip는 BOM이 없으면 **OS 기본 인코딩(cp949)** 으로
requirements.txt를 읽는다. 파일에 한글 주석이 있으면 설치가 통째로 실패한다.
```
UnicodeDecodeError: 'cp949' codec can't decode byte 0x80 in position 10
```
**대응**: `requirements.txt`를 **UTF-8 with BOM**으로 저장한다. pip는 BOM을
먼저 검사하므로 pip 버전·OS 로케일과 무관하게 동작한다. (2026-08-17 적용 완료)

### 2. 기본 python이 3.11 미만일 수 있다
이 프로젝트는 Python 3.11+ 가 필요하다. `python --version`이 3.9 등이면
venv 생성 시 버전을 명시한다.
```
py -3.11 -m venv .venv
```

## 팀 공용 DB 주의사항

`10.1.54.120:1521/XEPDB1`을 팀원 전체가 공유한다.

- 한 명이 DDL을 실행하면 **전원에게 반영**된다. `00_drop_all.sql` 실행 전 공지할 것
- `email`/`nickname`이 유일해야 해서 테스트 계정이 충돌한다.
  `test-{본인이름}@example.com` 식으로 구분해서 쓸 것
- XE는 동시 세션 수에 제약이 있어 `DB_POOL_SIZE=5`로 작게 잡아뒀다

### 사외에서 작업할 때

`10.1.54.120`은 **사내망 주소**라 집에서는 접속이 안 된다. 선택지:

| 방법 | 비고 |
|---|---|
| VPN | 사내망에 붙을 수 있으면 그대로 사용 |
| 로컬 Oracle XE 설치 | `db/00_create_user_local.sql`(SYS로 실행) → `01_schema.sql` → `.env`의 `DB_HOST=localhost` |
| 프론트엔드만 작업 | DB 없이 가능. `/api/health`가 503이어도 화면은 뜬다 |

`DB_HOST` 한 줄만 바꾸면 되도록 설계해뒀다.
